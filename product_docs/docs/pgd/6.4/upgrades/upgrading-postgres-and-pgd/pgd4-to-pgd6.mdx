Upgrade a PGD 4 cluster to PGD 6 and Postgres to a new major version at the same time, moving from HARP
Proxy to Connection Manager, using one of three approaches: [full
downtime](#upgrading-with-full-downtime), a [rolling upgrade in
place](#upgrading-with-a-rolling-upgrade-in-place), or a [rolling upgrade that replaces
nodes](#upgrading-with-a-rolling-upgrade-by-replacing-nodes) one at a time. If you're not also upgrading
Postgres, see [Upgrading PGD 4 to PGD 6](/pgd/current/upgrades/upgrading-pgd/pgd4-to-pgd6/) instead.

!!! Note
This procedure assumes HARP Proxy isn't co-located with a PGD node.
!!!

## Upgrading with full downtime

1.  Disconnect applications from the cluster, and stop HARP Proxy on every node running it:

    ```shell
    sudo systemctl stop harp-proxy
    ```

1.  Make sure Postgres is still running on every node. [`pgd node
    upgrade`](/pgd/latest/reference/cli/command_ref/node/upgrade/) needs the old instance running through
    its check and execute steps.
1.  On each node, one at a time or all at once, install the combined PGD 6 and new Postgres major version
    package (for example, `edb-pgd6-expanded-pg17`), alongside the existing PGD 4 and Postgres packages:

    ```shell
    dnf install edb-pgd6-cli edb-pgd6-expanded-pg<postgres_version> -y
    ```

    Package managers install each Postgres major version to its own path, so the running node and its
    current binaries are untouched.
1.  Create a fresh, empty data directory for the new Postgres version on each node using its
    [`initdb`](https://www.postgresql.org/docs/current/app-initdb.html), matching the old cluster's checksum
    and locale settings. Leave this new cluster shut down.
1.  Copy each node's old cluster's [`postgresql.conf` and
    `postgresql.auto.conf`](https://www.postgresql.org/docs/current/config-setting.html),
    [`pg_hba.conf`](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html), and `conf.d` directory
    (if present) into the new data directory, adjusting for any configuration parameters that changed
    between Postgres major versions.
1.  On each node, run `pgd node upgrade` with the `--check` option first to validate the upgrade without
    making changes:

    ```shell
    pgd node <node_name> upgrade --check \
      --old-bindir <old_bindir> \
      --new-bindir <new_bindir> \
      --old-datadir <old_datadir> \
      --new-datadir <new_datadir> \
      --database <database_name> \
      --username <install_user>
    ```

    `--old-bindir` and `--new-bindir` are the old and new Postgres installation's `bin` directories.
    `--old-datadir` and `--new-datadir` are the old cluster's data directory and the empty new data
    directory you created earlier. `--database` is the PGD-enabled database name, and `--username` is the
    cluster's install user. `--check` runs the PGD-specific validation and `pg_upgrade --check`, without
    modifying either cluster. See [Steps
    performed](/pgd/latest/reference/cli/command_ref/node/upgrade/#steps-performed) for exactly what
    `--check` does and doesn't run.
1.  Run `pgd node upgrade` again without `--check` to migrate the node's data into the new data directory,
    using the same options:

    ```shell
    pgd node <node_name> upgrade \
      --old-bindir <old_bindir> \
      --new-bindir <new_bindir> \
      --old-datadir <old_datadir> \
      --new-datadir <new_datadir> \
      --database <database_name> \
      --username <install_user>
    ```

    PGD itself upgrades to PGD 6 once you start the new data directory in the next step, with Connection
    Manager enabled by default, no extra step needed.
1.  Stop HARP manager on every node:

    ```shell
    sudo systemctl stop harp-manager
    ```

1.  Point Postgres at the new binaries and data directory on each node (for example, update the
    `postgres.service` file), then start it. Each node comes up on the new Postgres version and PGD 6, with
    Connection Manager already enabled. You don't need to start HARP manager again.
1.  Confirm every node has rejoined the cluster and is healthy:

    ```shell
    pgd nodes list
    ```

    Every node should show `ACTIVE` under `Join State` and `Up` under `Node Status`. Then continue to
    [Moving to Connection Manager](#moving-to-connection-manager) below.

## Upgrading with a rolling upgrade, in place

!!! Note
If your cluster uses CAMO, see [Upgrading a CAMO-enabled
cluster](/pgd/current/upgrades/planning_upgrade/#upgrading-a-camo-enabled-cluster) before performing this
procedure.
!!!

HARP Proxy continues routing on all nodes until the entire cluster is upgraded to PGD 6 or higher. It keeps
using its own leader-election mechanism throughout, since a 4.x cluster doesn't have a write leader. Start
the upgrade on a node that isn't the current HARP Proxy leader, where `<location>` is the HARP location
name (a data center or site defined in the HARP configuration, not a node name):

```shell
harpctl get leader <location>
```

Use the command-line utility [`pgd node
upgrade`](/pgd/latest/reference/cli/command_ref/node/upgrade/) to migrate each node's Postgres version and
move it to Connection Manager in the same pass. It wraps the standard
[`pg_upgrade`](https://www.postgresql.org/docs/current/pgupgrade.html), adding PGD-specific steps around it
so replication slots and origins carry over correctly.

For each node, one at a time, starting with a node that isn't the current HARP Proxy leader:

1.  Fence the node from HARP, then confirm it's fenced, so it doesn't become the leader partway through the
    upgrade:

    ```shell
    harpctl fence <node_name>
    harpctl get node <node_name>
    ```

1.  Make sure Postgres is still running on the node. `pgd node upgrade` needs the old instance running
    through its check and execute steps.
1.  Install the combined PGD 6 and new Postgres major version package (for example,
    `edb-pgd6-expanded-pg17`), alongside the existing PGD 4 and Postgres packages:

    ```shell
    dnf install edb-pgd6-cli edb-pgd6-expanded-pg<postgres_version> -y
    ```

    Package managers install each Postgres major version to its own path, so the running node and its
    current binaries are untouched.
1.  Create a fresh, empty data directory for the new Postgres version using its
    [`initdb`](https://www.postgresql.org/docs/current/app-initdb.html), matching the old cluster's checksum
    and locale settings. Leave this new cluster shut down.
1.  Copy the old cluster's [`postgresql.conf` and
    `postgresql.auto.conf`](https://www.postgresql.org/docs/current/config-setting.html),
    [`pg_hba.conf`](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html), and `conf.d` directory
    (if present) into the new data directory, adjusting for any configuration parameters that changed
    between Postgres major versions.
1.  Run `pgd node upgrade` with the `--check` option first to validate the upgrade without making changes:

    ```shell
    pgd node <node_name> upgrade --check \
      --old-bindir <old_bindir> \
      --new-bindir <new_bindir> \
      --old-datadir <old_datadir> \
      --new-datadir <new_datadir> \
      --database <database_name> \
      --username <install_user>
    ```

    `--old-bindir` and `--new-bindir` are the old and new Postgres installation's `bin` directories.
    `--old-datadir` and `--new-datadir` are the old cluster's data directory and the empty new data
    directory you created earlier. `--database` is the PGD-enabled database name, and `--username` is the
    cluster's install user. `--check` runs the PGD-specific validation and `pg_upgrade --check`, without
    modifying either cluster. See [Steps
    performed](/pgd/latest/reference/cli/command_ref/node/upgrade/#steps-performed) for exactly what
    `--check` does and doesn't run.
1.  Run `pgd node upgrade` again without `--check` to migrate the node's data into the new data directory,
    using the same options:

    ```shell
    pgd node <node_name> upgrade \
      --old-bindir <old_bindir> \
      --new-bindir <new_bindir> \
      --old-datadir <old_datadir> \
      --new-datadir <new_datadir> \
      --database <database_name> \
      --username <install_user>
    ```

    PGD itself upgrades to PGD 6 once you start the new data directory in the next step, with Connection
    Manager enabled by default, no extra step needed.
1.  Stop HARP manager on the node:

    ```shell
    sudo systemctl stop harp-manager
    ```

1.  Point Postgres at the new binaries and data directory (for example, update the `postgres.service` file),
    then start it. The node comes up on the new Postgres version and PGD 6, with Connection Manager enabled.
    You don't need to start HARP manager again.
1.  Unfence the node from HARP:

    ```shell
    harpctl unfence <node_name>
    ```

1.  Confirm the node is healthy and running the new Postgres version:

    ```shell
    pgd nodes list --versions
    ```

1.  Repeat for each remaining node, one at a time, until every node is running PGD 6 and the new Postgres
    version. Then continue to [Moving to Connection Manager](#moving-to-connection-manager) below.

For the full set of options and flags, see the [`pgd node
upgrade`](/pgd/latest/reference/cli/command_ref/node/upgrade/) command reference.

## Upgrading with a rolling upgrade, by replacing nodes

Instead of upgrading a node in place, join a new node that already has the combined PGD 6 and new Postgres
major version packages installed, then part and drop one of the existing PGD 4 nodes.

1.  [Provision a new node](/pgd/current/deploying/deploy-manual/03-installing-database-and-pgd/) with the
    combined PGD 6 and new Postgres major version packages already installed, for example
    `edb-pgd6-expanded-pg17`. Connection Manager is enabled on it by default.
1.  Join the new node to the cluster using a logical join:

    ```shell
    pgd node <node_name> setup --dsn "<new_node_dsn>" --cluster-dsn "<existing_node_dsn>" -D <pg_data>
    ```

    Don't use `bdr_init_physical`, it requires the source and joining node to run the same PGD version and
    the same Postgres major version, so it can't be used across a version change. See the [`pgd node
    setup`](/pgd/latest/reference/cli/command_ref/node/setup/) command reference for the full set of
    options.
1.  Wait for the new node to catch up with the cluster before routing traffic to it, then confirm it's
    healthy and running the new Postgres version:

    ```shell
    pgd nodes list --versions
    ```

    !!! Note
    How a newly joined PGD 6 node interacts with HARP's leader election and routing while the rest of the
    cluster is still on PGD 4 hasn't been confirmed for this procedure, including whether any extra step is
    needed to bring the new node into HARP's view of the cluster. Verify with EDB Support or engineering
    before relying on this path.
    !!!

1.  Update your application's connection configuration to include the new node once it's ready to take
    traffic.
1.  Part one of the nodes still running PGD 4 and HARP Proxy, then decommission it:

    ```shell
    pgd node <node_name> part
    ```
1.  Repeat for each remaining PGD 4 node, one at a time, until the whole cluster is on PGD 6 and the new
    Postgres version. Then continue to [Moving to Connection Manager](#moving-to-connection-manager) below.

While nodes are on mixed Postgres major versions, avoid using any feature or DDL syntax that's only
available in the newer version, until every node has been replaced.

## Moving to Connection Manager

Once every node is running PGD 6 and the new Postgres version, regardless of which upgrade path you took,
finish moving the cluster off HARP Proxy and onto Connection Manager.

1.  Confirm every node is running the new version:

    ```shell
    pgd nodes list --versions
    ```

1.  Run the following query from any of the upgraded nodes to ensure
    [SCRAM](https://www.postgresql.org/docs/current/auth-password.html) hashes are the same across all
    nodes for each user. This query is required before applications switch to Connection Manager:

    ```sql
    DO $$
    DECLARE
        rec RECORD;
        command TEXT;
        password TEXT;
    BEGIN
        FOR rec IN SELECT rolname,rolpassword FROM pg_authid WHERE rolcanlogin = true AND rolpassword like 'SCRAM-SHA%'
        LOOP
            password := rec.rolpassword;
            command := 'ALTER ROLE ' || quote_ident(rec.rolname) || ' WITH ENCRYPTED PASSWORD ' || quote_literal(password);
            EXECUTE command;
        END LOOP;
    END;
    $$;
    SELECT bdr.wait_slot_confirm_lsn(NULL,NULL);
    ```

1.  Enable node group routing as appropriate for your global or local routing requirement. For local
    routing, enable it on subgroups. For global routing, enable it on the top group:

    ```sql
    SELECT bdr.alter_node_group_option(node_group_name := '<group_name>', config_key := 'enable_routing', config_value := true::TEXT);
    ```

1.  Switch your application to Connection Manager.
1.  Stop any HARP manager and HARP Proxy services still running:

    ```shell
    sudo systemctl stop harp-manager
    sudo systemctl stop harp-proxy
    ```
1.  Confirm the cluster is healthy:

    ```shell
    pgd cluster show --health
    ```
