AIDB records semantic knowledge base (semantic KB) operations in a durable audit log. The log helps an operator identify who performed an operation, which semantic KB and object it affected, which function ran, and the relevant operation details.

The log is stored in an extension-private table. You read it only through [`aidb.semantic_kb_audit()`](../reference/semantic-knowledge-bases#aidbsemantic_kb_audit).

The log records completed operations only. It doesn't record failed attempts, denied calls, or rolled-back transactions.

## When to use the audit log

Use the audit log to answer questions such as:

- **Who changed a description?** Filter on `op => 'annotate'`, and read `actor_name`, `login_name`, and `ts`. For a change that used `force`, `detail` also holds the wording that was discarded.
- **Which objects do searches return, and how often?** Filter on `op => 'retrieve'`. Each record has the search options, the number of results, and the objects returned. It doesn't have the search text.
- **Which semantic aliases are being run?** Filter on `op => 'execute'`, and group by `object_ref`.

For example, the following query shows who changed descriptions in `analytics_kb` over the last 30 days:

```sql
SELECT ts, actor_name, login_name, object_ref, detail
FROM aidb.semantic_kb_audit(
    kb_name => 'analytics_kb',
    op => 'annotate',
    since => now() - interval '30 days'
)
ORDER BY ts DESC;
```

## What's recorded

AIDB records these operations:

| Operation                                                                                            | Category                       |
|------------------------------------------------------------------------------------------------------|--------------------------------|
| Searching a semantic KB with `aidb.semantic_kb_search()`                                             | `retrieve`                     |
| Executing a [semantic alias](semantic-aliases)                                                       | `execute`                      |
| Adding or removing an object description                                                             | `annotate`                     |
| Proposing, approving, or rejecting an object description. See [Descriptions and curation](curation). | `propose`, `approve`, `reject` |
| Adding or deleting a [relationship](relationships)                                                   | `write`                        |
| Importing query history, and accepting a relationship candidate                                      | `write`, `approve`             |
| Creating a semantic KB, including any context you set, and updating a semantic KB's context          | `admin`                        |
| Processing context into reviewable proposals                                                         | `propose`                      |
| Pruning audit records                                                                                | `admin`                        |

AIDB doesn't record these operations:

- Deleting a semantic KB with `aidb.delete_semantic_kb()`.
- Refreshing a semantic KB with `aidb.refresh_semantic_kb()`.
- Changing the auto-processing mode with `aidb.update_semantic_kb_auto_processing()`.
- Searches that run through the `semkb_<name>_search` tool of a semantic KB's managed agent plugin. Searches through the native `semantic_kb_search` tool and the SQL function are recorded.

Audit logging is part of the operation. An audit record commits or rolls back with the operation it describes.

Every search and every alias execution writes a record. A semantic KB that's searched often can generate many records, so plan to [prune the log](#retention-and-pruning) regularly.

## Reading the audit log

Use `aidb.semantic_kb_audit()` to read audit records. You can call it as a superuser, as the extension owner, or as a role that has been granted `EXECUTE` on the function. `aidb_users` members can't call it unless they have that grant.

The following example returns recent description changes for `analytics_kb`:

```sql
SELECT
    ts,
    op,
    func,
    caller_kind,
    actor_name,
    login_name,
    object_ref,
    detail
FROM aidb.semantic_kb_audit(
    kb_name => 'analytics_kb',
    op => 'annotate',
    func => 'add_comment_to_object',
    since => now() - interval '7 days',
    limit_rows => 100
)
ORDER BY ts DESC;
```

All filters are optional:

- `kb_name` limits results to one semantic KB. When it's `NULL`, the function returns records from all semantic KBs.
- `op` limits results to one operation category.
- `func` limits results to the exact value recorded in the `func` column.
- `since` returns records from the specified time onward.
- `limit_rows` controls the maximum number of records returned. The default is 100.

Results are ordered from newest to oldest. The function returns these columns:

| Column        | Description                                                                                                      |
|---------------|------------------------------------------------------------------------------------------------------------------|
| `ts`          | When AIDB wrote the record.                                                                                      |
| `kb_name`     | The semantic KB the record belongs to.                                                                           |
| `op`          | The operation category. See [Operation categories and functions](#operation-categories-and-functions).         |
| `func`        | The function that ran.                                                                                           |
| `caller_kind` | How the operation arrived. See [Caller, actor, and login identities](#caller-actor-and-login-identities).      |
| `actor_name`  | The effective role that invoked the operation.                                                                   |
| `login_name`  | The role that authenticated the database session.                                                                |
| `object_ref`  | What the operation named as its subject, such as an alias name or a table. Searches don't have an object reference. |
| `detail`      | JSON that's specific to the operation. See [Operation details](#operation-details).                              |

For all parameters and columns, see [`aidb.semantic_kb_audit`](../reference/semantic-knowledge-bases#aidbsemantic_kb_audit).

## Operation categories and functions

The `op` column groups related operations into categories. The `func` column records the function that ran. It isn't always the name of the SQL function you called, so filter on values you've seen in your own log.

| Category   | Operations                                                                  | Function names                                                  |
|------------|-----------------------------------------------------------------------------|-------------------------------------------------------------------------|
| `retrieve` | Semantic KB searches.                                                       | `semantic_kb_search`                                                    |
| `execute`  | Semantic alias execution.                                                   | `execute_semantic_alias`                                                |
| `annotate` | Applied object-description changes.                                         | `add_comment_to_object`                                                 |
| `write`    | Relationship and query-history changes.                                     | `add_relationship`, `delete_relationship`, `import_query_history`       |
| `propose`  | Changes awaiting review, and context processing.                            | `propose_comment`, `process_context`                                    |
| `approve`  | Review decisions that approve a change.                                     | `accept_relationship_candidate`                                         |
| `reject`   | Review decisions that reject a change.                                      |                                                                         |
| `admin`    | Configuration and maintenance operations.                                   | `create_semantic_kb`, `update_context`, `semkb_audit_prune`             |

For example, an applied comment written with `aidb.add_comment_to_object()` is recorded with `op = 'annotate'` and `func = 'add_comment_to_object'`. A comment held for review under [curation](curation) is recorded with `op = 'propose'` until a reviewer approves or rejects it.

## Caller, actor, and login identities

Each record identifies who performed the operation:

- `caller_kind` is how the operation arrived. In AIDB 7.9.0 it's always `direct`, including for operations that an agent or an MCP client runs.
- `actor_name` is the effective role that invoked the operation.
- `login_name` is the role that authenticated the database session.

`actor_name` and `login_name` can differ when a session uses `SET ROLE`. AIDB stores the role's name as it was when AIDB wrote the record, so renaming a role later doesn't change existing records.

Semantic alias execution can also run the alias query as a different role. That execution role is recorded in the `execute_role` field of `detail`. It's separate from both the actor and login identities.

## Operation details

The `detail` column contains JSON that's specific to the operation. AIDB never stores free text that a person typed.

For a semantic KB search, `detail` contains:

- The search options: `top_k`, `rrf_k`, `min_similarity`, `include_proposed`, `sources`, and `entity_types`.
- The query length in characters, in `query_chars`.
- The number of results, in `result_count`. This is always the true number of results.
- `hits`, a list of the results. Each entry has `source_type`, `entity_type`, and `object_ref`. The list is limited to 100 entries and 16 KiB, and each `object_ref` is limited to 256 characters. When a limit shortens the list, `hits_truncated` is `true`.

The natural-language search text isn't stored.

For semantic alias execution, `detail` contains:

- The execution role.
- The names of the arguments you supplied and the number of bound parameters.
- The result count.
- The number of semantic KBs that own the alias.

Argument values and query result rows aren't stored.

For object-description changes, `detail` contains:

- The object type.
- Whether the change was an add or an edit.
- Whether `force` was used.
- The previous wording that a forced change discarded.

For context processing, `detail` contains counts, the outcome, and the IDs of the relationships that attempt wrote. It never contains the context or the model's raw response.

Audit detail is limited to 32 KiB. If the serialized detail is larger, AIDB replaces all of it with a marker that has `truncated` set to `true` and records the original size in bytes in `orig_bytes`.

## Operations that affect multiple semantic KBs

An object or semantic alias can belong to more than one semantic KB. AIDB writes one audit record for each affected semantic KB, so each KB has its own reviewable and independently prunable history.

A semantic alias that no semantic KB owns doesn't create an audit record when it runs.

## Retention and pruning

Nothing deletes audit records automatically. There is no background worker for pruning. You prune records manually, or from a scheduler such as `pg_cron`.

Audit records stay after you delete the semantic KB they describe. You can prune them afterward by using the deleted KB's name, as described in [Pruning audit records](#pruning-audit-records).

### Setting the default prune age

The `aidb.semkb_audit_retention` parameter sets the default age that `aidb.semkb_audit_prune()` uses when you don't specify one. The default is `30 days`. Only a superuser can change it. Set it at the database level:

```sql
ALTER DATABASE my_database
    SET aidb.semkb_audit_retention = '90 days';
```

A zero interval makes `aidb.semkb_audit_prune()` delete nothing. A negative or invalid interval raises an error before any records are deleted. Changing this parameter doesn't schedule or run pruning. See [Configuring AIDB parameters](../install/configure#semantic-knowledge-base-audit-log).

### Pruning audit records

Use `aidb.semkb_audit_prune()` to delete expired records for one semantic KB.

Specify an age explicitly:

```sql
SELECT aidb.semkb_audit_prune(
    'analytics_kb',
    interval '90 days'
);
```

Omit the interval to use `aidb.semkb_audit_retention`:

```sql
SELECT aidb.semkb_audit_prune('analytics_kb');
```

The function works on one semantic KB at a time. To prune several semantic KBs, call it once for each, for example from a scheduled job.

The function returns the number of deleted records, not counting the record it writes about itself. It deletes records in batches of 5,000 rows. It writes one `admin` audit record with the retention interval, the number of deleted records, and the number of batches. It writes that record even when it deletes nothing.

The caller must be a member of the semantic KB's owner role. `aidb.create_semantic_kb()` sets that role to the extension owner, so in practice only the extension owner, members of the extension owner's role, and superusers can prune. To prune the records of a semantic KB that no longer exists, you must be the extension owner or a superuser. A caller who isn't authorized gets an error with SQLSTATE `42501`.

## Transactions and read-only sessions

The audit record is written in the same transaction as the operation:

- If the operation commits, the audit record commits with it.
- If the operation rolls back, the audit record also rolls back. A semantic alias execution that fails leaves no audit record.
- If writing the audit record fails, the operation fails instead of completing without its record. This includes searches.

In a read-only transaction or on a hot standby, searches and alias executions continue but don't write an audit record. This means searches that run on a standby aren't audited.
