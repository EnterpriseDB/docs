The MCP endpoint authenticates every agent as a Postgres login role. The grants on that role decide what it can list and call, so provisioning an agent is ordinary Postgres administration: create a role with a password, allow it in `pg_hba.conf`, and grant it access to the profile roles and tools it needs. A profile role is an ordinary `NOLOGIN` Postgres role that holds privileges — group them by function (read-only, read-write, and so on) and grant them to agent roles instead of granting privileges directly.

## Step 1: Grant the role what it needs

| Requirement                                               | Why                                                                                                                                                                                                                |
|-----------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `LOGIN` and a password                                    | The agent presents the username and password in the HTTP Basic header on every call, and the endpoint opens a Postgres connection with them.                                                                       |
| A matching `local` line in `pg_hba.conf`                  | The endpoint connects over the server's Unix socket, so `local` lines apply (see [How it works](../mcp-endpoint#how-it-works) for the TCP fallback). Use a password method such as `scram-sha-256`, never `trust`.                |
| `EXECUTE` on `aidb.get_mcp_tools()` and `aidb.run_tool()` | Membership in `aidb_users` provides both. Without them, `tools/list` fails with a permission error.                                                                                                                |
| Grants on the objects the tools touch                     | A tool runs as the agent, so the agent needs `USAGE` on the schema and the table privileges its tools use.                                                                                                         |

Keep the agent role itself free of direct privileges and grant it profile roles instead. Revoking a profile role from an agent takes effect on the agent's next call, since every call opens a fresh connection.

See [Provisioning example](provisioning-example) for a worked example that creates an agent role and profile roles together.

## What an agent can do once provisioned

After the [MCP handshake](connecting-a-client), an agent's calls behave according to its own grants, not any setting on the endpoint itself.

| Call                                | Behavior                                                                                                                                    |
|--------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| `tools/list`                        | Returns every tool in the catalog regardless of the caller's grants — the [listing shows what exists, not what the caller may run](../mcp-endpoint#what-tools-the-endpoint-surfaces). |
| `tools/call` on a catalog tool       | Succeeds if the role holds the privileges the tool's SQL needs. Otherwise Postgres returns `permission denied` and no rows are affected.      |
| `tools/call` with a wrong password   | `isError` with `password authentication failed`.                                                                                             |

Arguments are bound as query parameters, and arguments a tool didn't declare are rejected with `unknown argument '<name>'`, so an agent can't ask a tool to run as someone else.

See [Provisioning example](provisioning-example) for these behaviors demonstrated with two agents holding different grants.

## Revoking an agent

Revoke with ordinary role changes:

```sql
REVOKE <profile_role> FROM <agent_role>;   -- narrows what the agent can do, takes effect on its next call
ALTER ROLE <agent_role> NOLOGIN;           -- the agent can't connect at all
DROP ROLE <agent_role>;                    -- after reassigning or dropping anything the role owns
```

See [Provisioning example](provisioning-example#revoking-an-agent) for this applied to a specific agent.
