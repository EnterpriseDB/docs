title: Error log
description: Inspect, clear, and retry failed pipeline records using the per-pipeline error log in EDB Postgres AI.
---

Every pipeline has a dedicated error log table. When a record fails at any step, the log captures the source record ID, which step failed, the operation, and the error message.

## Key features

- **Per-pipeline error log table.** Failures land in `{source_schema}.pipeline_{pipeline_name}_errors`. A single bad record does not block the batch.
- **Four error categories.** Record-level errors (`RecordTemporary`, `RecordPermanent`) leave the rest of the batch running. Pipeline-level errors (`PipelineTemporary`, `PipelinePermanent`) stop the step entirely. See [`aidb.ErrorBlocking`](../reference#aidberrorblocking).
- **Postgres `WARNING` per error.** Each logged error also emits a warning. Toggle with [`aidb.pipeline_error_warnings`](../reference#aidbpipeline_error_warnings); errors persist to the log regardless.
- **Lifecycle bound to the pipeline.** The error log table is created with the pipeline and dropped when the pipeline is deleted. Pipelines created before 7.4.0 get their table during the upgrade. Writes happen inside the failing step's transaction, so a successful step never leaves orphan log rows and a failure never loses its record.

## How it works

- Each error is classified along two dimensions: scope (record vs pipeline) and temporality (temporary vs permanent). `RecordTemporary` currently fires only for model rate-limit errors. `RecordPermanent` covers bad input data (corrupt PDF, malformed HTML, invalid UTF-8). `PipelineTemporary` covers transient external faults (object store outage, model service timeout). `PipelinePermanent` is the catch-all for misconfiguration (deleted model, invalid step config).
- The query and summary functions return empty results for any pipeline whose error log table is missing.
- Do not drop the error log table manually. As of 7.4.0, the source `DELETE` handlers and post-step cleanup raise an error if the table is missing.

## Inspecting errors

Use [`aidb.get_error_logs`](../reference#aidbget_error_logs) to inspect a pipeline's error log:

```sql
SELECT * FROM aidb.get_error_logs('my_pipeline');
__OUTPUT__
 id | source_id | part_ids | pipeline_step | step_operation | error_message                          | error_category    | failed_at                  | retry_count | last_retry_at
----+-----------+----------+---------------+----------------+----------------------------------------+-------------------+----------------------------+-------------+---------------
  3 | doc_99    | {0,2}    |             2 | ChunkText      | text segment exceeded maximum length   | RecordPermanent   | 2026-04-10 14:32:01.123+00 |           0 |
  2 | doc_42    | {0}      |             1 | ParsePdf       | failed to extract text from page 0     | RecordPermanent   | 2026-04-10 14:31:58.456+00 |           0 |
  1 | doc_7     |          |             1 | ParsePdf       | corrupt PDF header                     | RecordPermanent   | 2026-04-10 14:31:55.789+00 |           0 |
(3 rows)
```

Filter by source record, step number, or error category:

```sql
SELECT * FROM aidb.get_error_logs(
    'my_pipeline',
    p_source_id => 'doc_42'
);
```

```sql
SELECT * FROM aidb.get_error_logs(
    'my_pipeline',
    p_pipeline_step  => 1::SMALLINT,
    p_error_category => 'RecordPermanent'
);
```

Paginate with `p_limit` and `p_offset`:

```sql
SELECT * FROM aidb.get_error_logs('my_pipeline', p_limit => 20, p_offset => 40);
```

See the [Pipelines API reference](../reference#aidbget_error_logs) for parameter and return type details.

### Error summaries

Error counts grouped by step, operation, and category for one pipeline:

```sql
SELECT * FROM aidb.get_error_log_summary('my_pipeline');
__OUTPUT__
 pipeline_step | step_operation | error_category    | error_count | latest_failed_at
---------------+----------------+-------------------+-------------+----------------------------
             1 | ParsePdf       | RecordPermanent   |           2 | 2026-04-10 14:31:58.456+00
             2 | ChunkText      | RecordPermanent   |           1 | 2026-04-10 14:32:01.123+00
(2 rows)
```

Same rollup across all pipelines:

```sql
SELECT * FROM aidb.get_all_error_summaries();
__OUTPUT__
 pipeline_name | pipeline_step | step_operation | error_category    | error_count | latest_failed_at
---------------+---------------+----------------+-------------------+-------------+----------------------------
 my_pipeline   |             1 | ParsePdf       | RecordPermanent   |           2 | 2026-04-10 14:31:58.456+00
 my_pipeline   |             2 | ChunkText      | RecordPermanent   |           1 | 2026-04-10 14:32:01.123+00
 pdf_ingester  |             1 | ParsePdf       | PipelinePermanent |           1 | 2026-04-10 15:00:12.000+00
(3 rows)
```

## Recovering from failures

### Clearing errors

Delete specific error log entries by ID:

```sql
SELECT aidb.clear_error_logs('my_pipeline', ARRAY[1, 3]);
__OUTPUT__
 clear_error_logs
------------------
                2
(1 row)
```

The return value is the number of rows actually deleted. Clearing is ID-based, so review entries with `aidb.get_error_logs` before removing them.

### Retrying failed records

Use [`aidb.retry_pipeline_errors`](../reference#aidbretry_pipeline_errors) to re-run failed records by error log ID:

```sql
SELECT * FROM aidb.retry_pipeline_errors('my_pipeline', ARRAY[1, 2]);
__OUTPUT__
 error_id | status   | error_message
----------+----------+--------------------------------------------
        1 | resolved |
        2 | failed   | failed to extract text from page 0
(2 rows)
```

Each result row reports one of three statuses:

- `resolved`: the record processed cleanly and the error log entry was deleted.
- `failed`: the record failed again. The new error stays in the log with an incremented `retry_count` and an updated `last_retry_at` timestamp.
- `skipped`: pipeline-level error (see below).

Retry re-runs every step from the start for each affected source record, not just the step that originally failed. That keeps the retry path uniform across pipeline shapes and avoids reconstructing a mid-pipeline envelope. Earlier-step work is repeated; retry is sized for small batches a user runs after diagnosing a failure.

Only one retry can run against a given pipeline at a time. A concurrent call from another session fails fast with "A retry operation is already in progress for this pipeline." Retry does not block `aidb.run_pipeline` or the background worker.

#### Pipeline-level errors

Pipeline-level errors (NULL `source_id`) record batch failures that aren't tied to a specific record. They can't be retried per record, so `aidb.retry_pipeline_errors` returns `status='skipped'` and leaves the entry in the log:

```sql
SELECT * FROM aidb.retry_pipeline_errors('my_pipeline', ARRAY[7]);
__OUTPUT__
 error_id | status  | error_message
----------+---------+--------------------------------------------------------------
        7 | skipped | Pipeline-level error (no source record); fix and re-run.
(1 row)
```

Fix the underlying issue (model availability, config, deleted model), re-run the pipeline so the step processes cleanly, then dismiss the entry with `aidb.clear_error_logs`.

#### Source deleted between failure and retry

If the source record was removed from the source table or volume between the original failure and the retry call, the result is `status='failed'` with a "source record no longer exists" message. The call does not raise.

#### Aggregated error messages

When a single source record fans out into many failing parts (for example, a PDF that parses into many pages that all fail at a later step), the returned `error_message` aggregates the first 10 messages with a trailing `... and N more (see error log table)` line. The full set stays in the error log table and can be queried with `aidb.get_error_logs`.

## Automatic cleanup

Error log entries clear without `aidb.clear_error_logs` or `aidb.retry_pipeline_errors` in three cases:

- Source record deleted. The live `DELETE` trigger, background worker `DELETE` processing, and volume stale-state cleanup all remove matching error log entries alongside their destination rows.
- Source envelope reaches the destination on a later run. The pipeline executor clears entries scoped by `(source_id, part_ids)` so part-granular successes do not wipe sibling errors.
- Pipeline-level rows (NULL `source_id`) for a step clear after that step next runs cleanly. Errors written by a concurrent failing executor during that run are preserved.

Pipeline deletion drops the entire error log table.

## End-to-end example

A short walkthrough using a three-document source where one row has a corrupt PDF, one parses but produces an oversized chunk, and a third hits a model rate limit on the embedding step.

```sql
-- 1. Run the pipeline. None of the three failures abort the batch.
SELECT aidb.run_pipeline('my_pipeline');

-- 2. Inspect the resulting errors.
SELECT id, source_id, error_category
FROM aidb.get_error_logs('my_pipeline');
__OUTPUT__
 id | source_id | error_category
----+-----------+-----------------
  3 | doc_99    | RecordPermanent
  2 | doc_42    | RecordPermanent
  1 | doc_7     | RecordPermanent
(3 rows)

-- 3. The pipeline now reports PartialErrors and surfaces the counts.
SELECT pipeline, "Status", "count(record errors)", "count(blocking errors)"
FROM aidb.pipeline_metrics WHERE pipeline = 'my_pipeline';
__OUTPUT__
   pipeline   |    Status     | count(record errors) | count(blocking errors)
--------------+---------------+----------------------+------------------------
 my_pipeline  | PartialErrors |                    3 |                      0
(1 row)

-- 4. After fixing the upstream rate-limit issue, retry just the rate-limited row.
SELECT * FROM aidb.retry_pipeline_errors('my_pipeline', ARRAY[3]);
__OUTPUT__
 error_id | status   | error_message
----------+----------+---------------
        3 | resolved |
(1 row)

-- 5. Dismiss the two permanent failures after triage.
SELECT aidb.clear_error_logs('my_pipeline', ARRAY[1, 2]);
__OUTPUT__
 clear_error_logs
------------------
                2
(1 row)

-- 6. Status returns to UpToDate.
SELECT pipeline, "Status" FROM aidb.pipeline_metrics WHERE pipeline = 'my_pipeline';
__OUTPUT__
   pipeline   |  Status
--------------+----------
 my_pipeline  | UpToDate
(1 row)
```

## Pipeline status integration

Error counts also appear in the [`aidb.pipeline_metrics`](../reference#aidbpipeline_metrics) view. The pipeline's [status](../reference#aidbpipelinestatus) reports `PartialErrors` when some records failed and the rest processed normally, or `BlockingErrors` when a pipeline-level error stopped the step entirely.

See [Observability](./observability/) for more on monitoring pipeline health.
