Upgrade from 2026.9 to 2026.10.

> **Role:** Infrastructure engineer

## Prerequisites

- Administrative access to the Kubernetes cluster (`kubectl`, `helm`).
- Required tools:
    - `helm` (latest version recommended)
    - `kubectl`
    - [`edbctl`](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/edbctl/), the Hybrid Manager CLI — see the [edbctl compatibility matrix](/edbctl/latest/compatibility_matrix/) for the supported version.

## Upgrade 2026.9 → 2026.10

This release changes the telemetry stack that powers Query Diagnostics: ClickHouse partially replaces Prometheus/Thanos, and the `pg_stat_ch` extension replaces `edb_stat_monitor` as the source of query-level monitoring data. Because of this, moving a Postgres cluster onto the new operand images requires two manual actions beyond the usual HM version bump. Complete the steps in the order given:

1. Create new secrets.
1. Upgrade the operator to `2.2` or later, if it isn't already.
1. Update `spec.beaconAgent.provisioning.operandSetVersions` to whitelist both the current and new operand-sets.
1. Update `spec.version` and trigger the HM upgrade.
1. For each Postgres cluster you want to move onto the new operand-set, perform the cluster's major/minor upgrade, then manually create the `pg_stat_ch` extension.

### Create new secrets

Before upgrading, create the new secrets required for this release:

```shell
edbctl hm create-install-secrets --version v2026.10.0
```

For more CLI options, see [edbctl hybrid-manager](/edbctl/latest/using/edbctl_hybrid_manager/). To customize your component's secrets, see [Customizing secrets](/edb-postgres-ai/current/hybrid-manager/install/configuration/customizing_secrets/).

### Upgrade the operator

!!!Note Red Hat OpenShift
On RHOS, upgrade the operator through OperatorHub (OLM) by switching the subscription channel to `stable`. See [Upgrade the operator on Red Hat OpenShift](upgrade_operator_rhos). Do not use `edbctl hm upgrade-operator` on RHOS.
!!!

The commands below use `edb-hcp-operator-system` — use the namespace where your operator is actually installed. If you migrated from the bootstrap method, the conversion transfers Helm ownership onto `edbpgai-bootstrap`, so use that namespace instead.

Upgrade the `edb-hcp-operator` Helm chart using `edbctl`:

```shell
edbctl hm upgrade-operator \
  --release-name edb-hcp-operator \
  --namespace edb-hcp-operator-system \
  --registry-uri docker.enterprisedb.com/pgai-platform \
  --registry-username pgai-platform \
  --registry-password <password>
```

Or upgrade directly with Helm:

!!!note
`<OPERATOR_VERSION>` refers to the operator chart version, which follows its own `2.x` versioning scheme and is separate from the HM version (`2026.10`). HM 2026.10 requires operator version `2.2` or later — the same version 2026.9 required, so no action is needed if you're already on `2.2` or later.
!!!

1. Create the values file:

    ```shell
    cat <<EOF > edb-hcp-operator.values.yaml
    controllerManager:
      manager:
        image:
          repository: docker.enterprisedb.com/pgai-platform/edb-hcp-operator/manager
          tag: <OPERATOR_VERSION>
    imagePullSecrets:
      - name: edb-cred
    EOF
    ```

1. Run the upgrade:

    ```shell
    helm upgrade --install \
      --version <OPERATOR_VERSION> \
      --values edb-hcp-operator.values.yaml \
      -n edb-hcp-operator-system \
      edb-hcp-operator enterprisedb-edbpgai/edb-hcp-operator
    ```

### Enable the Major/Minor upgrade path for existing clusters

Starting in HM 1.3.2, operand images carry an operand-set version, and the beacon agent only treats images matching an allowed pattern as discoverable. IR 2026.7–2026.9 shipped operand-set `1.2.x`. HM 2026.10 requires operand-set `1.3.0` or later and only works with operand images from that operand-set onward.

Existing Postgres clusters keep running on their current `1.2.x` operand images and stay healthy through the HM upgrade — moving the platform forward doesn't touch them. But during the transition window, the in-UI **Major/Minor upgrade** action for those clusters fails unless both operand-sets are whitelisted.

!!!important
If `spec.beaconAgent.provisioning.operandSetVersions` whitelists only the new `1.3.x` pattern (or is otherwise missing the `1.2.x` pattern), HM can no longer discover a cluster's current `1.2.x` image. The Major/Minor upgrade dialog then fails to resolve that image, and a `PGImageMissing` alert may fire on reconcile.
!!!

Before you upgrade any cluster, whitelist both the previous and new operand-sets on the `HybridControlPlane` (HCP) CR — the source of truth for this setting. Don't edit the `beacon-agent-k8s-config` configmap directly; it's reconciled from the HCP CR and a direct edit will drift or revert.

```yaml
spec:
  beaconAgent:
    provisioning:
      operandSetVersions:
        - 1\.2\.[0-9]+    # previous operand-set (current cluster images) — keeps them discoverable
        - 1\.3\.[0-9]+    # new operand-set shipped with IR 2026.10
```

Apply it via `values.yaml` during the HM upgrade, or post-upgrade with `kubectl`:

```shell
# Inspect the current value
kubectl get hcp <name> -o jsonpath='{.spec.beaconAgent.provisioning.operandSetVersions}{"\n"}'

# Patch to whitelist both operand-sets
kubectl patch hcp <name> --type=merge -p '{
  "spec": {"beaconAgent": {"provisioning": {"operandSetVersions": ["1\\.2\\.[0-9]+", "1\\.3\\.[0-9]+"]}}}
}'
```

With both whitelisted, HM can discover the current `1.2.x` image again, the Major/Minor upgrade dialog resolves it, and the upgrade path — including extensions — becomes available so you can move clusters up to a `1.3.x` operand.

Follow this phased approach as you migrate:

| Phase | `operandSetVersions` | Action |
| --- | --- | --- |
| 1 — Transitional | `1\.2\.[0-9]+`, `1\.3\.[0-9]+` | After upgrading HM to 2026.10, whitelist both so existing `1.2.x` clusters stay discoverable and the Major/Minor upgrade path works. |
| 2 — Migration | `1\.2\.[0-9]+`, `1\.3\.[0-9]+` | Upgrade each cluster from its `1.2.x` operand to a `1.3.x` operand, then manually create the `pg_stat_ch` extension on that cluster (see below). |
| 3 — Cleanup | `1\.3\.[0-9]+` | Once no cluster references a `1.2.x` operand, remove the `1.2.x` pattern to enforce the new operand-set. |

!!!warning
Don't remove the `1.2.x` pattern until every cluster has completed migration. Removing it while a cluster still runs a `1.2.x` image makes that image undiscoverable again, and the Major/Minor upgrade for that cluster fails with the same error.
!!!

### Enable `pg_stat_ch` on each migrated cluster

After a cluster's image is on a `1.3.x` operand, HM-managed clusters already have `pg_stat_ch` in `shared_preload_libraries` and configured for OpenTelemetry — moving the image forward doesn't, by itself, create the extension in the database. You must do that manually, once per cluster:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_ch WITH SCHEMA edb_internals;
```

!!!important
Run this on every database the cluster monitors, not just `edb_admin`. `pg_stat_ch` must be created per-database — it isn't enough to create it once on the default database.
!!!

Until you create the extension on a database, Query Diagnostics data for that database keeps coming from `edb_stat_monitor`. HM retains `edb_stat_monitor` — it's still used internally — and only removes it in IR 2026.11, so there's no need to drop it yourself.

No cluster restart is needed for this step.

#### Self-managed clusters (external CNPG and bare-metal)

Self-managed clusters — external CNPG (pg4k) clusters and bare-metal installations — need a separate, more involved process than HM-managed clusters, because `pg_stat_ch` isn't bundled with their images automatically.

For external CNPG clusters running the enterprise build (pg4k), discover a suitable operand image that includes `pg_stat_ch` from HM's Asset Library, then follow the same major/minor upgrade and extension-creation steps as above. OSS CNPG doesn't support mounting the extension from the official CloudNativePG extension catalogue, so you need a custom image that installs the EDB build of `pg_stat_ch`.

For bare-metal installations, install `pg_stat_ch` and configure it to point at your ClickHouse server before creating the extension. For the full procedure — package installation, `shared_preload_libraries`, and the OpenTelemetry settings — see [Monitoring Postgres with pg_stat_ch](/clickhouse/latest/monitoring_postgres/) in the EDB Postgres AI for ClickHouse documentation.

### Upgrade Hybrid Manager

1. Update `spec.version` to `v2026.10.0` in your `HybridControlPlane` manifest and apply it:

    ```shell
    kubectl apply -f hybridmanager.yaml
    ```

1. Trigger the upgrade:

    ```shell
    kubectl annotate hybridcontrolplane edbpgai --overwrite edbpgai.com/ready-for-upgrade=true
    ```

1. Monitor progress:

    ```shell
    kubectl get hybridcontrolplane edbpgai -w
    ```

### Postgres cluster restart

This release updates the Barman Cloud Plugin to version 0.15.0, which brings significantly faster restore times for compressed backups.

!!!warning
Upgrading to HM 2026.10 restarts every Postgres cluster to apply the updated plugin.
!!!

Plan a maintenance window for this upgrade. For details, see the [HM 2026.10 release notes](/edb-postgres-ai/innovation-release/hybrid-manager/release_notes/).

### Scenario behavior change: `core` now includes `observability`

From this release onward, selecting the `core` installation scenario automatically includes `observability`, because `core` now requires ClickHouse. This applies on fresh installs, upgrades, and existing installations alike — if your `HybridControlPlane` manifest lists only `core`, upgrading to 2026.10 deploys the `observability` components alongside it. No action is required, but be aware of this if you're tracking which components are deployed in a `core`-only installation.

## Upgrading multi-DC deployments

In a [multi-DC deployment](/edb-postgres-ai/current/hybrid-manager/install/configuration/multi_dc/), all locations must run the same HM version. Upgrade the primary location first, then upgrade each data-only secondary location to the same version immediately after. For the full procedure, see [Upgrading a multi-DC deployment](/edb-postgres-ai/current/hybrid-manager/install/configuration/multi_dc/multi-dc/#upgrading-a-multi-dc-deployment).

## Troubleshooting upgrade job failures

The upgrade operator creates and manages upgrade jobs automatically. If an upgrade job fails and doesn't reach a `Complete` or `Succeeded` state, the operator pauses and retries. It doesn't proceed to apply updated manifests until the job succeeds.

!!!note
The operator owns and manages the upgrade job exclusively. Don't create upgrade jobs manually, as doing so can conflict with the operator's reconciliation loop.
!!!

To investigate a failed upgrade job:

1. Check the status of upgrade jobs:

    ```shell
    kubectl get jobs -n edbpgai-bootstrap -l edbpgai.edb.com/hm-upgrader=true
    ```

1. Check the logs for the failed job:

    ```shell
    kubectl logs job/<job-name> -n edbpgai-bootstrap
    ```

    Replace `<job-name>` with the name of the failed job from the previous command.

1. Check the `HybridControlPlane` status for upgrade-related events:

    ```shell
    kubectl describe hybridcontrolplane edbpgai
    ```

If the issue persists after the operator retries, contact EDB support with the job logs.
