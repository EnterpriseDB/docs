Upgrade from 2026.10.1 to 2026.11.

> **Role:** Infrastructure engineer

## Prerequisites

- Administrative access to the Kubernetes cluster (`kubectl`, `helm`).
- Required tools:
    - `helm` (latest version recommended)
    - `kubectl`
    - [`edbctl`](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/edbctl/), the Hybrid Manager CLI, version 1.11 or later — see the [edbctl compatibility matrix](/edbctl/latest/compatibility_matrix/) for the supported version.

## Upgrade 2026.10.1 → 2026.11

Starting in 2026.11, HM reads its install secrets from the `edb-system` namespace instead of `default`, and Chat Agent stops relying on the inference services you configured in HM. HM moves the `edb-object-storage` secret for you during the upgrade, but you must create the other install secrets — such as `hm-portal-bootstrap`, `langflow-secret`, and the `db-*` secrets — in `edb-system` yourself before you upgrade. If you use Chat Agent, see [Chat Agent model credentials](#chat-agent-model-credentials) to keep it working after the upgrade.

Complete the steps in the order given:

1. Upgrade the operator to `2.3` or later, if it isn't already.
1. Create secrets, including Chat Agent model credentials if you use Chat Agent.
1. Update `spec.version` (and `spec.scenarios`, if you're enabling Chat Agent) and trigger the HM platform upgrade.

### Upgrade the operator

!!!note
HM 2026.11 requires operator version `2.3` or later. If your operator is already on `2.3` or later, skip this section.
!!!

!!!Note Red Hat OpenShift
On RHOS, upgrade the operator through OperatorHub (OLM) by switching the subscription channel to `stable`. See [Upgrade the operator on Red Hat OpenShift](upgrade_operator_rhos). Do not use `edbctl hm upgrade-operator` on RHOS.
!!!

The operator's namespace depends on how it was installed. Fresh operator installs use `edb-hcp-operator-system`. Installations converted from the bootstrap method usually remain in `edbpgai-bootstrap`. Set `OPERATOR_NS` to the namespace of your operator release:

```shell
OPERATOR_NS=$(helm list -A --filter '^edb-hcp-operator$' --no-headers | awk '{print $2}')
echo "$OPERATOR_NS"
```

If `echo` prints nothing, your release isn't named `edb-hcp-operator` and the environment variable `OPERATOR_NS` is empty. Run `helm list -A` to find its actual name and namespace, then set `OPERATOR_NS` to that namespace yourself.

Choose one of the following methods to upgrade the `edb-hcp-operator` Helm chart.

#### Using edbctl (recommended)

Run the upgrade:

```shell
edbctl hm upgrade-operator \
  --release-name edb-hcp-operator \
  --namespace "$OPERATOR_NS" \
  --registry-uri docker.enterprisedb.com/pgai-platform \
  --registry-username pgai-platform \
  --registry-password <password>
```

#### Using Helm

1. Create the values file:

    ```shell
    cat <<EOF > edb-hcp-operator.values.yaml
    controllerManager:
      manager:
        image:
          repository: docker.enterprisedb.com/pgai-platform/edb-hcp-operator/manager
          tag: <OPERATOR_VERSION>
    imagePullSecrets:
      - name: edb-cred
    EOF
    ```

1. Run the upgrade:

    ```shell
    helm upgrade --install \
      --version <OPERATOR_VERSION> \
      --values edb-hcp-operator.values.yaml \
      -n "$OPERATOR_NS" \
      edb-hcp-operator enterprisedb-edbpgai/edb-hcp-operator
    ```

### Create secrets

#### Install secrets in `edb-system`

Before upgrading, use `edbctl` 1.11 or later to create the install secrets in the `edb-system` namespace:

```shell
edbctl hm create-install-secrets --version v2026.11.0
```

Use the same `--scenario` options that you listed in `spec.scenarios`. For more information, see [Create component secrets](/edb-postgres-ai/current/hybrid-manager/install/install_guide/environment_prep/#create-component-secrets).

For more CLI options, see [edbctl hybrid-manager](/edbctl/latest/using/edbctl_hybrid_manager/). To customize your component's secrets, see [Customizing secrets](/edb-postgres-ai/current/hybrid-manager/install/configuration/customizing_secrets/).

#### Chat Agent model credentials

In 2026.11, Chat Agent no longer depends on the inference services that you configured in HM. HM drops the inference service configuration from versions before 2026.10.1 in 2026.10.1, and it doesn't migrate that configuration to 2026.11.

If you want to use Chat Agent after the upgrade, add the `chatbot` scenario to `spec.scenarios` when you update the manifest in [Upgrade Hybrid Manager](#upgrade-hybrid-manager). Then create the `chatbot-model-creds` secret yourself with `edbctl`, using the `chatbot` scenario:

```shell
edbctl hybrid-manager create-install-secrets --version v2026.11.0 --scenario chatbot
```

The secret holds the endpoint, model name, and API key for each model that Chat Agent uses. For the settings and options, see [Customizing Chat Agent model secrets](/edb-postgres-ai/current/hybrid-manager/install/configuration/customizing_secrets/chatbot_secrets). For how Chat Agent uses the models, see [Configuring the Chat Agent](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/chat_agent/configure).

!!!note
Create the secret before you upgrade. HM doesn't restart Chat Agent when it first creates the secret. If you create it after the upgrade, restart Chat Agent yourself. See [Changing the models later](/edb-postgres-ai/current/hybrid-manager/install/configuration/customizing_secrets/chatbot_secrets#changing-the-models-later).
!!!

### Upgrade Hybrid Manager

1. In your `HybridControlPlane` manifest (`hybridmanager.yaml`), update the `spec.version` field to `v2026.11.0`:

    ```yaml
    apiVersion: edbpgai.edb.com/v1alpha1
    kind: HybridControlPlane
    metadata:
      name: edbpgai
    spec:
      version: v2026.11.0 # was v2026.10.1
    ```

    If you want to use Chat Agent, also add `chatbot` to `spec.scenarios`:

    ```yaml
    spec:
      scenarios:
        - core
        - chatbot
      version: v2026.11.0 # was v2026.10.1
    ```

    See [Chat Agent model credentials](#chat-agent-model-credentials) to create the required secret.

1. Apply the updated manifest:

    ```shell
    kubectl apply -f hybridmanager.yaml
    ```

1. Monitor progress:

    ```shell
    kubectl get hybridcontrolplane edbpgai -w
    ```

## Upgrading multi-DC deployments

In a [multi-DC deployment](/edb-postgres-ai/current/hybrid-manager/install/configuration/multi_dc/), all locations must run the same HM version. Upgrade the primary location first, then upgrade each data-only secondary location to the same version immediately after. For the full procedure, see [Upgrading a multi-DC deployment](/edb-postgres-ai/current/hybrid-manager/install/configuration/multi_dc/multi-dc/#upgrading-a-multi-dc-deployment).

## Troubleshooting upgrade job failures

The upgrade operator creates and manages upgrade jobs automatically. If an upgrade job fails and doesn't reach a `Complete` or `Succeeded` state, the operator pauses and retries. It doesn't proceed to apply updated manifests until the job succeeds.

!!!note
The operator owns and manages the upgrade job exclusively. Don't create upgrade jobs manually, as doing so can conflict with the operator's reconciliation loop.
!!!

To investigate a failed upgrade job:

1. Check the status of upgrade jobs:

    ```shell
    kubectl get jobs -A -l edbpgai.edb.com/hm-upgrader=true
    ```

1. Check the logs for the failed job:

    ```shell
    kubectl logs job/<job-name> -n <namespace>
    ```

    Replace `<job-name>` and `<namespace>` with the failed job from the previous command.

1. Check the `HybridControlPlane` status for upgrade-related events:

    ```shell
    kubectl describe hybridcontrolplane edbpgai
    ```

If the issue persists after the operator retries, contact EDB support with the job logs.
