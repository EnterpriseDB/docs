Hybrid Manager (HM) provides a set of open-source applications that can be deployed and managed directly from the HM console.

!!! important Disclaimer
The OSS Library apps are third-party open-source software provided for convenience. EDB doesn't develop, maintain, or provide support for these applications and isn't responsible for any issues, data loss, or service disruptions arising from their use. For support, refer to each application's official documentation and community resources.
!!!

!!! warning Disclaimer
OSS Library requires internet connectivity and isn't supported in air-gapped environments. Attempting to use it in an air-gapped environment may result in errors or unexpected behavior.
!!!

## Deployment and architecture

Apps deploy as containerized applications within your HM Kubernetes environment using a `.yaml` package file. This deployment ensures database traffic remains entirely within your private network (VPC/VNET) and security perimeter. The architecture supports horizontal scaling and external PostgreSQL application databases for high availability.

!!! important
When deploying apps that require backend database connections, use a dedicated database within your Postgres cluster for each app. Apps sharing the same database risk migration failures due to schema conflicts during the initialization phase.
!!!

!!! note
OSS Library apps support Community PostgreSQL as the backend application database. pgAdmin 4 also supports EDB Postgres Advanced Server (EPAS).
!!!

!!! note GKE ARM64: minimum persistent volume size is 4Gi
If you deploy OSS Library apps on a Google Kubernetes Engine (GKE) cluster that uses `arm64` `n4a` (Google Axion) machine family with `hyperdisk-balanced` storage class which enforces a minimum persistent volume size of **4Gi**. When you deploy any OSS Library app that provisions a persistent volume (for example, HammerDB, pgBadger, or pgAdmin 4), set the app's storage-size field to `4Gi` or larger. If you leave the storage size below 4Gi, the app's `PersistentVolumeClaim` stays in the `Pending` state and the deployment never reaches `Ready`. See [Known issues](/edb-postgres-ai/latest/hybrid-manager/overview/known_issues/#oss-library-app-deployment-fails-on-gke-arm64-when-the-requested-storage-size-is-less-than-4gi) for details.
!!!

!!! warning GKE ARM64: HammerDB isn't supported
The HammerDB OSS Library app can't be deployed on GKE ARM64 clusters. The HammerDB pod spec is missing the ARM64 toleration required to schedule onto ARM64 worker nodes, so the pod stays `Pending` and the app never becomes healthy. See [Known issues](/edb-postgres-ai/latest/hybrid-manager/overview/known_issues/#hammerdb-app-doesnt-become-healthy-on-gke-arm64-due-to-missing-arm64-toleration) for details and the recommended alternative.
!!!

## Apps installed before upgrading to HM 2026.11

Starting with HM 2026.11, HM stores the resources that manage your OSS Library apps in the `edb-system` namespace instead of the `default` namespace. The upgrade doesn't move the apps that you installed before it. Those apps keep running and serving, but HM still tracks them in the `default` namespace.

!!!important Recreate OSS Library apps after the upgrade
For apps installed before the upgrade, EDB recommends that you delete the app and create it again. The same advice applies when you move an app to a newer version. OSS Library apps are third-party software, and EDB can't know what changes between versions. A recreated app is a new installation with an empty volume, so export any data that you need first.
!!!

What to expect for an app installed before the upgrade:

- The app keeps running, and you can still edit it.
- If you delete the app from the HM console, HM removes only its entry. The app keeps running, with its storage and route, until you remove the old copy by hand (step 4 below).

To recreate an app:

1. Export any data that you need from the app. A recreated app is a new installation with an empty volume.
1. In the HM console, delete the app. The old copy keeps running.
1. In the HM console, install the app again from the OSS Library.
1. Remove the old copy of the deleted app. List the apps in the `default` namespace and find the one with the name of the app that you deleted:

    ```shell
    kubectl get beaconapp -n default
    ```

    Then delete it:

    ```shell
    kubectl delete beaconapp <app-id> -n default
    ```

    Replace `<app-id>` with the value in the `NAME` column. This uninstalls the old app, including its storage.

!!!warning Only remove the old copy of an app that you already deleted
Don't run `kubectl delete beaconapp` for an app that you still use, even if you edited it or upgraded it after the HM upgrade. The old copy and the new one share the same Kubernetes namespace, so deleting the old copy uninstalls the running app and deletes its data.
!!!

Apps that you install after the upgrade are tracked in `edb-system` and need no extra steps.
