The **Logs** tab for a cluster in Hybrid Manager (HM) provides real-time and historical insight into its internal operations, system events, and extension-level activity. Use it for debugging, diagnostics, and monitoring the health of individual pods.

The **Logs** tab serves as a centralized logging interface that lets you trace events, warnings, and system activity for each pod in a cluster. It helps database administrators and Kubernetes operators quickly identify operational issues, such as misconfigured extensions, heartbeat failures, or missing components.

## Filtering by service

Every log stream that HM collects records the service that produced it. Use the **Service Name** menu to select which service's logs the tab displays:

-   **Postgres** &mdash; logs from the Postgres database itself.
-   **Beacon Agent** &mdash; logs from the EDB Postgres AI agent, which collects monitoring data and pushes it to HM.

By default, the tab displays Postgres logs only. This keeps the view focused on database activity instead of mixing in agent output.

Select **Beacon Agent** when you're investigating data collection problems rather than database problems, for example, missing metrics or gaps in monitoring data.

## Filtering by pod

The **Pod** column shows the pod that produced each log line. Select a pod name to filter the list to that pod alone, which isolates issues affecting a specific part of the cluster.

## Filtering by time range

Use the date selector to filter logs within a specific time frame, improving focus during incident investigation.

## Filtering by log field

You can also build filters on the structured fields of a log entry. Each filter combines a **Field**, an **Operator** (**Contains** or **Not Contains**), and a value.

The available fields are:

-   **Level** &mdash; the log level of the entry.

-   **Severity** &mdash; the Postgres error severity of the entry: `INFO`, `LOG`, `WARNING`, `ERROR`, or `FATAL`. Postgres can also emit `PANIC`.

-   **Backend Type** &mdash; the type of Postgres backend that produced the entry, for example, `client backend`.

-   **Container** &mdash; the container in the pod that produced the entry.

-   **Custom Filter** &mdash; a free-text search against a single field. Select **Any** to search the whole entry, or target **Process ID**, **Session ID**, **Virtual Transaction ID**, or **Transaction ID**.

Entries include detailed error messages, such as missing extensions or failed queries, to help with root cause analysis.

## Log details

The **Logs** tab displays the following columns:

| Column    | Description                                                                                                                                                     |
|-----------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Timestamp | Indicates when the log event occurred (UTC).                                                                                                                    |
| Pod       | The pod where the event originated. Select the pod name to filter the list to that pod.                                                                          |
| Event     | A brief description of the event, such as extension errors or heartbeat checks. Also provides the severity label, such as `INFO` or `WARNING`, for the event.    |

## Common uses

-   Verifying that monitoring extensions, such as `query_advisor` and `edb_stat_monitor`, are active and correctly configured.

-   Investigating errors related to missing or non-functional database extensions.

-   Tracking regular system-level events, such as pod heartbeats.

-   Auditing recent changes or anomalies in cluster behavior.

-   Confirming that the EDB Postgres AI agent is collecting and pushing monitoring data as expected.
