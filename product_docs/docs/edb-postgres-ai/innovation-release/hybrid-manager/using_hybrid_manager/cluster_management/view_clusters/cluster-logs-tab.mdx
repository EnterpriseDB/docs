The **Logs** tab for a cluster in Hybrid Manager (HM) displays log entries from the cluster's pods. Use it to trace events, warnings, and errors while debugging. You can filter the entries by service, pod, time range, and the structured fields of each entry.

## What the tab displays by default

By default, the **Logs** tab displays Postgres logs only. If you're looking for entries that aren't there, change the **Service Name** menu:

-   **Postgres** &mdash; Logs from the Postgres service. This option is the default.

-   **Beacon Agent** &mdash; Logs from the [EDB Postgres AI agent](../../monitoring/mon_ext_dbs/mon_with_agent), which collects monitoring data and pushes it to HM. Select this when you're investigating data collection problems, such as missing metrics or gaps in monitoring data, rather than database problems.

    For external self-managed clusters that run on hosts or virtual machines, the agent doesn't send its own logs to HM, so this option shows no entries. To check the agent's logs on these clusters, view the agent's output on the host where it runs.

    For external self-managed CloudNativePG (CNPG) clusters, this option shows the logs of the agent container that runs in each Postgres instance pod, once log collection is set up as described in [Availability](#availability).

To isolate Postgres logs, filter by service rather than by container. On CNPG-based clusters, the `postgres` container also carries instance-manager output, so filtering by container doesn't return the database's own logs alone.

When filtering by log field, **Severity** is the error severity reported by Postgres itself (`INFO`, `LOG`, `WARNING`, `ERROR`, `FATAL`, or `PANIC`), while **Level** is the log level recorded by the collector. Filter on **Severity** when you want the database's own assessment of an event.

## Availability

Log collection isn't available for every cluster type:

-   For HM-managed clusters, HM collects logs by default.

-   For external self-managed clusters that run on hosts or virtual machines, log collection is turned off by default. The EDB Postgres AI agent collects Postgres logs only when log collection is enabled and the agent runs on the same host as the Postgres node it collects from. If this tab is empty for a self-managed cluster, check that `general.metrics.push.include_logs` is `true`, that `logs.disabled` is `false` for the relevant node, and that the node's `dsn` points to the local host. See [Fine-tuning monitoring data collection](../../monitoring/mon_ext_dbs/mon_with_agent/configure_agent/fine_tune_monitoring.mdx).

-   For external self-managed CNPG clusters that run in your own Kubernetes cluster, the agent doesn't read Postgres log files itself, and `general.metrics.push.include_logs` doesn't apply. HM receives the cluster's logs only when the OpenTelemetry collector that's included in the agent's Helm chart is installed (`additionalCharts.opentelemetry-collector.install: true`). The collector forwards the logs of the Postgres instance pods labeled `k8s.enterprisedb.io/beacon: enabled`, including the agent container in each pod, so both the **Postgres** and **Beacon Agent** options show entries. See [Installing the EDB Postgres AI agent](../../monitoring/mon_ext_dbs/monitoring_ext_k8s_clusters/mon_ext_k8s_clusters.mdx).

-   For external cloud service provider (CSP)-managed databases, such as AWS RDS, HM doesn't collect logs and this tab has no data. See [Metrics support scope](../../monitoring/monitoring_console/support_scope.mdx).

## Timestamps and retention

The tab displays timestamps in Coordinated Universal Time (UTC), not your local time zone. Account for this difference when you correlate entries with logs from other systems.

HM retains log entries for 30 days by default, so the time range you select can't reach further back than that. The tab refreshes every 10 seconds. See [Metrics refresh intervals](../../monitoring/monitoring_console/metrics_latency.mdx).

## Querying logs beyond this tab

HM collects logs into Loki. For queries this tab can't express, such as searching across several clusters at once, use [Grafana's Explore option](../../monitoring/monitoring_grafana/grafana_explore.mdx) to query Loki directly.
