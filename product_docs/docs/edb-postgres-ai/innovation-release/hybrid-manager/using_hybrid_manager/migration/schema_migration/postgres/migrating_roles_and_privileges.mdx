By default, schema migration creates schema objects only: every migrated object is owned by the migration role — the database user you already configured for the EDB DMS agent in writer mode — and no roles, privileges, or row-level security (RLS) policies come across from the source.

For migrations to self-managed destinations, you can optionally migrate the source cluster's authorization model as well — its roles, object ownership, privileges, and RLS policies — so your applications keep working against the same permissions after cutover. See [Migrating roles, ownership, and privileges](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/migration_guides/self_managed_pg_to_self_managed_pg/configuring_dms_agent/#migrating-roles-ownership-and-privileges) in the self-managed Postgres-to-Postgres guide to turn it on, [DBCONFIG_DATABASES_0__ROLE_MIGRATION_ENABLED](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/dms_agent_reference/#dbconfig_databases_0__role_migration_enabled) for the setting itself, and [Role, ownership, and privilege migration limitations](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/limitations/#role-ownership-and-privilege-migration-limitations) for what doesn't carry over.

## Why this is available only for self-managed destinations

Creating roles and reassigning object ownership on the destination requires a superuser connection — role management is a cluster-wide privilege in Postgres, not something scoped to a single database or schema. When you migrate to a self-managed destination, you run the EDB DMS agent in writer mode yourself, so you can give it a superuser connection to make this possible. Migrations to HM-managed destinations use an HM-managed writer that doesn't currently expose this option, so role migration isn't available there, regardless of migration scope.

Role migration is also Postgres-specific — it relies on extracting role and privilege definitions in a form only a Postgres source produces — so it isn't available for Oracle sources. And because it works by attaching roles, ownership, and privileges to schema objects as they're created, it only has an effect when your migration scope includes schema (**Schema and data** or **Schema only**); a **Data only** migration never creates schema objects, so there's nothing for role migration to attach to.

## How role migration works

When enabled, DMS migrates roles and their dependent objects in two phases, timed around the rest of schema migration:

1.  **At the start of schema migration**, before any schema objects are created, DMS creates the source cluster's roles on the destination cluster, preserving attributes such as `LOGIN`, `CREATEROLE`, and `VALID UNTIL`. This has to happen first, since later schema objects reference these roles as owners or grantees.
2.  **At migration finalization**, DMS applies role memberships, object ownership (`ALTER ... OWNER TO`), privilege grants, default privileges, and RLS policies, and enables RLS on tables that had it enabled on the source. This runs last because these statements reference objects that must already exist.

Because of this timing, the destination's authorization model is complete only once the migration reaches the **Completed** state — plan any post-migration privilege verification for after that point, not while the migration is still in progress.

!!!warning Passwords are never migrated
Role definitions are extracted from the source without password hashes, so DMS creates `LOGIN` roles on the destination without a password. Set new passwords on the destination before applications authenticate with the migrated roles.
!!!

## Excluding roles from migration

You can tell DMS to leave specific roles alone instead of migrating them — typically roles that already exist on the destination (most often the bootstrap superuser, `postgres` or `enterprisedb`), or roles you'd rather manage yourself outside of DMS. Roles are matched against a set of regular expression patterns you provide; see [excluding roles](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/migration_guides/self_managed_pg_to_self_managed_pg/configuring_dms_agent/#migrating-roles-ownership-and-privileges) for the steps.

When a role is excluded, DMS doesn't create it on the destination, and at finalization it skips any ownership, grant, default privilege, or policy statement that references it — logging a warning for each one skipped. The objects those statements would have touched keep the migration role as their owner instead, so you'd need to reassign ownership or re-grant privileges by hand afterward to fully match the source's authorization model.

!!!note
If an RLS policy references an excluded role, the policy itself is skipped, but RLS stays enabled on its table — RLS is a table-level setting, independent of any one policy. The table denies access to non-owners until you recreate the policy on the destination.
!!!

## Idempotency and conflicts with existing roles

DMS marks every role it creates with a comment, `dms:migrated:<migration ID>`, so that restarting schema migration doesn't try to recreate roles it already made — a role carrying the marker is simply skipped on retry.

If a role with the same name already exists on the destination *without* that marker, DMS has no way to tell whether it matches the source's definition. Rather than guess, it treats this as a conflict: schema migration fails outright, with an error listing every conflicting role name. See [resolving a role migration conflict](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/migration_guides/self_managed_pg_to_self_managed_pg/configuring_dms_agent/#migrating-roles-ownership-and-privileges) for how to get past it.
