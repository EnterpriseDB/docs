This terminology is important to understand EDB Data Migration Service (DMS) functionality.

## Change data capture (CDC)

CDC is a set of software design patterns used to determine and track changes in data sets by calculating *deltas*. EDB DMS uses CDC to stream changes from one database cluster to another.

## EDB DMS agent

The DMS agent is a tool that can register databases for migration. In reader mode, it registers databases as a source for migrations. In writer mode, it registers them as a destination.

After you register the source and destination databases, the DMS agent works with DMS to perform data migrations.

!!!note 
    In Hybrid Manager (HM) version 1.3 and later, the [EDB Data Migration Service agent](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/installing_agent/), packaged as `cdcagent`, replaces legacy DMS Reader and DMS Writer. 

    To ensure compatibility, use the DMS agent on all HM 1.3 and later deployments. For HM deployments on version 1.2 and earlier, use the separately packaged EDB DMS Reader and EDB DMS Writer.

### EDB DMS agent in reader mode

When running in reader mode, the DMS agent uses Debezium to perform CDC operations on the source database and Kafka/Object storage to produce messages containing the change events.

Install the DMS agent on your source machine. Alternatively, if your source database runs on a machine managed by a cloud provider that you don't have admin access to, you can also install it on an auxiliary machine that has access to your source database. 

Then configure and launch it in reader mode when performing any type of migrations, as this mode allows you to connect to and read the source.

### EDB DMS agent in writer mode 

When running in writer mode, the DMS agent consumes CDC records from Kafka/Object storage to replicate and apply changes on the destination database.

If the destination for your migration is an HM-managed database, you don't need to install and launch the EDB DMS agent in writer mode because the DMS component that comes with HM already includes a built-in writer.

If the destination is a self-managed database, install an additional DMS agent on your destination machine. Then configure and launch it in writer mode as that mode allows you to connect to and migrate data to self-managed destinations.

## EDB Postgres AI agent 

The [EDB Postgres AI agent](/tools/agent/), packaged as `beacon-agent`, and formerly known as HM or beacon agent, is a tool that provides database observability, monitoring, usage reporting, and more. In the context of migrations, the EDB Postgres AI agent performs a migration assessment for each database you register with it. It also performs schema extraction for subsequent schema migration — for Oracle sources, this feeds the [Migration Portal integration](/edb-postgres-ai/current/hybrid-manager/using_hybrid_manager/migration/schema_migration/migration_portal/); for Postgres sources, it enables the unified schema migration workflow when you select the **Schema and Data** or **Schema Only** scope.

## Auxiliary machine

An auxiliary machine is a Linux-based server (bare metal, VM, or local) dedicated to running the EDB DMS agent for database migrations. This machine acts as the migration engine, capable of connecting to various source and destination databases, whether local or remote. 

This machine can be the same host as where you have a source or destination database and the same host where you have the HM running. The only requirement is a Linux operating system, since that's the only platform currently supporting the EDB DMS agent.

## Migration types

When [creating migrations](migration_guides/self_managed_pg_to_hm_managed/migrating_data/#creating-a-migration), you can choose whether to perform the migration using the **Snapshot**, **Snapshot + Streaming**, or **Streaming** option.

### Snapshot migration

When you select the **Snapshot** option, DMS captures an image of your database at a specific moment. This point-in-time copy is then used for the migration. Any new inserts and updates performed on the source database after the snapshot is taken aren't replicated to the destination database.

### Snapshot + Streaming migration

When you select the **Snapshot + Streaming** option, DMS begins with a snapshot to establish a baseline copy and then constantly employs CDC to apply subsequent changes. This approach ensures data consistency during migration. DMS continues to stream any data updates performed on the source database to the destination database until you [mark the migration as completed](migration_guides/self_managed_pg_to_hm_managed/migrating_data/#performing-the-cutover).

### Streaming migration

When you select the **Streaming** option, DMS skips the snapshot entirely and starts streaming changes from the source database's current position at the moment the migration is created. No existing data is copied — only inserts, updates, and deletes that occur after the migration starts are replicated to the destination.

Use this option when you don't need (or don't want) an initial bulk copy — for example, when the destination already holds the historical data from another load process, or in fallback replication scenarios where you only need to keep two databases in sync going forward.

!!!note Limitations

- If your tables only ever receive inserts (for example, an append-only log or event table), you don't need to pre-load the destination — DMS just inserts new rows as they arrive on the source.
- If your tables receive updates or deletes on rows that existed before the migration started, load that historical data on the destination first. `DELETE` operations for rows that were never loaded on the destination are safely ignored (no error). `UPDATE` operations for rows that were never loaded aren't guaranteed to create the row on the destination, so don't rely on updates alone to backfill missing history.
- Streaming always starts from the source's current position (for example, the latest LSN for Postgres or SCN for Oracle). Starting from a specific, earlier LSN or SCN isn't supported yet.
!!!

## Migration scope

When creating a migration, you select a scope that determines whether the migration includes schema, data, or both.

### Data Only

Migrates data only. Use this option when you have already imported the schema to the destination database manually. The schema must be in place before the migration begins.

### Schema and Data

Migrates schema and data in a single managed workflow. HM imports the schema automatically from the Migration Portal project created when you registered your source database, handles constraint ordering during migration, and reapplies deferred constraints after the migration completes. This scope requires the source database to be registered with the EDB Postgres AI agent.

### Schema Only

Migrates schema only, without transferring data. Useful for setting up the destination database structure before running a data-only migration.

## Large object (LO) migration

Postgres large objects (`pg_largeobject`) are data — arbitrary binary content referenced by an `oid`, such as file attachments. Enable large object migration with the [`LO_SNAPSHOT_ENABLED`](dms_agent_reference/#postgres-large-object-migration-parameters) parameter, for the **Schema and Data** scope.

Because logical decoding can't capture large object writes, DMS copies large object content separately from the regular snapshot and streaming phases, in one bulk operation when you [mark the migration as completed](migration_guides/self_managed_pg_to_hm_managed/migrating_data/#performing-the-cutover). Because large object ownership is preserved, the role that owns each large object on the source must also exist, under the same name, on the destination.

## Migration destination types

When [creating migrations](migration_guides/self_managed_pg_to_hm_managed/migrating_data/#creating-a-migration), you can choose whether to perform a migration to managed Postgres or to external Postgres.

### Managed Postgres

Managed Postgres destinations are databases created and managed through HM. You can select any of the database clusters created in the project where you're performing the migration as possible migration destinations. 

### External Postgres

External Postgres destinations are databases created outside of HM that you fully manage. To choose an external Postgres database as a migration destination, you must first install and configure the [DMS agent](terminology.mdx#edb-dms-agent) and configure it in writer mode to allow the DMS to connect to the self-managed database and perform write operations on it.

## Apache Kafka

[Apache Kafka](https://kafka.apache.org/) is an open-source, distributed-event streaming platform used by thousands of companies for high-performance data pipelines, streaming analytics, data integration, and mission-critical applications. EDB DMS uses Kafka to manage data streaming from the source to the destination database.

## Debezium

[Debezium](https://debezium.io/) is a Java-based, open-source platform for CDC that's supported by the Red Hat community. When running in reader mode, the EDB DMS agent uses Debezium to perform reading operations and capture data changes on the source database.

## Legacy terminology

### EDB DMS Reader

In HM versions 1.2 and earlier, EDB Data Migration Service Reader, packaged as `cdcreader`, is a tool that uses Debezium to perform CDC operations on the source database and Kafka to produce messages containing the change events.

Install and configure DMS Reader when performing any type of migrations, as it allows you to connect to and read the source. If the destination for your migration is an HM-managed database, you don't need to install [DMS Writer](terminology.mdx#edb-dms-writer). If the destination is another self-managed database, install [DMS Writer](terminology.mdx#edb-dms-writer).

### EDB DMS Writer

In HM versions 1.2 and earlier, EDB Data Migration Service Writer, packaged as `cdcwriter`, is a tool that uses CDC records to replicate and apply changes on the destination database.

Install and configure DMS Writer on your destination machine when performing migrations to self-managed destination databases, as it allows you to connect to self-managed destinations. Also install [DMS Reader](terminology.mdx#edb-dms-reader) for any type of migrations.
