A switchover is a planned role change. It promotes a replica cluster to primary and demotes the current primary to a replica.

[comment]: # "Open question #2: The UI and CLI warnings ship in 2026.11. Should this page land now in both the IR and 1.4, with the warning text added in 2026.11? Does Switchover Primary exist in 1.4?"

!!!warning Both clusters must be able to reach each other before you switch over
Before the new primary starts accepting writes, it must copy the last changes from the current primary over the network. If the new primary can't reach the current primary's connection endpoint, the switchover can't finish, and neither cluster accepts writes until the connection is restored.

This requirement matters most when your clusters are in different locations, for example different regions, data centers, or virtual private clouds (VPCs).
!!!

## Before you start a switchover

Complete these checks before you start a switchover:

1.  Check that each cluster can reach the other. Traffic must flow in both directions between the two clusters' connection endpoints on port 5432. Each cluster must also be able to reach your backup object storage.

    [comment]: # "Open question #3: Is port 5432 in both directions correct, plus reachability to backup object storage?"

1.  Check each cluster's network access type. Private access works only if the two locations are connected. For example, they can share a network or use VPC peering, a virtual private network (VPN), or a private interconnect. Public access works as long as your firewalls and allowed IP ranges permit traffic between the two locations. You can mix public and private access, but only if the clusters can still reach each other.

1.  If you recently changed a cluster's network access type, wait. Changing between public and private gives the cluster a new connection address. Don't switch over until the new address is assigned and resolvable from the other location.

1.  Check that the replica cluster is healthy and actively replicating from the primary.

## Switching over to a replica cluster

To switch over to a replica cluster:

1.  From the project page, select **Clusters > Postgres Clusters**, and then select the cluster.

1.  From the detailed view of the cluster, select **Quick Actions > Switchover Primary**.

    [comment]: # "Open question #4: What's the CLI command for a switchover? Should it be documented here?"

    If **Switchover Primary** is unavailable, the cluster can't be switched over at the moment. Hover over the option to see the reason.

    [comment]: # "Open question #5: Which cluster states disable Switchover Primary? The tooltip says 'Cannot switchover primary now.'"

1.  In the Switchover dialog, in **Promoting to Primary**, select the replica cluster to promote. The current primary appears under **Demoting to Replica**.

1.  To confirm, enter `promote <replica cluster name>` in the field. For example, `promote Replica Cluster B`.

1.  Select **Confirm Switchover**.

After a few minutes, the **Replica Clusters** section of the **Overview** tab shows the promoted replica cluster with the **Primary** badge and the former primary with the **Replica** badge.

## If a switchover doesn't finish

If the clusters can't reach each other, you might see these symptoms:

-   The new primary stays in the Promoting to primary cluster state.
-   Both clusters reject writes with `cannot execute INSERT in a read-only transaction`.

[comment]: # "Open question #6: Do the state 'Promoting to primary cluster' and the error 'cannot execute INSERT in a read-only transaction' match what users see?"

To recover:

-   Restore connectivity between the two clusters. The switchover then finishes on its own.
-   Don't delete or restart the cluster's pods. It doesn't help, and the pods aren't recreated until the switchover finishes.
-   Don't retry the switchover.
-   If you can't restore connectivity, contact EDB Support. Recovering without the old primary can lose the most recent transactions and requires rebuilding the other cluster.

[comment]: # "Open question #7: Is 'contact EDB Support' the right guidance when connectivity can't be restored?"

## Switchover versus forced failover

A switchover is a planned role change. It needs both clusters online and able to reach each other.

[comment]: # "Open question #8: Is forced failover available in the UI or CLI? If so, what's it called, so we can add steps?"

A forced failover is for when the primary's location is lost or unreachable. It promotes the replica without waiting for the old primary, so any changes that hadn't reached the replica yet are lost. Use it only when you can't recover the primary in time. For the failover procedure in a multi-data-center deployment, see [Manual failover](/edb-postgres-ai/current/hybrid-manager/install/configuration/multi_dc/multi-dc/#manual-failover).
