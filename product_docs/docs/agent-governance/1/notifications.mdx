Use notifications to find out when an agent's denial pattern changes, without watching the [Agents](./agents) page. EDB Agent Governance posts a message to a webhook when `aidb` blocks an agent's attempt to switch role. It also posts a message when an agent starts or stops getting denied repeatedly. You get one message for each change in state, not one for every denied action.

You configure one webhook URL for each Postgres (aidb_otel) instance. Slack incoming webhooks work as-is. Any HTTPS endpoint that accepts a JSON `POST` works too, so you can also send signals to your own incident or ticketing tools.

## Before you begin

Confirm the following before you configure a webhook:

- You're signed in as an administrator. Only administrators can configure notifications.
- The chart values `bff.aidbOtelEnabled` and `bff.governanceDecisionsEnabled` are both `true`, which is the default. See [Configuration values](./installing#configuration-values).
- You've registered a Postgres (aidb_otel) instance. See [Connecting an aidb database](./connecting_aidb).
- You have a webhook URL. For Slack, create an incoming webhook for the channel that receives the messages.

## Configuring a webhook

Configure a webhook on each instance you want to send notifications:

1. Open the Configure Instances page and select the bell icon on the instance row.

1. Enter the Webhook URL. The dashboard encrypts the URL and later shows only its host name.

1. Choose which signals to send:

    - Escalation blocked — On by default. `aidb` refused an attempt by the agent to switch role, for example `SET ROLE`.
    - Repeated denials — Off by default. The agent's denial rate over the last hour reached the threshold. Set the threshold (default 20%) and the minimum number of governed actions before the rate counts (default 10). These defaults match the Repeated signal on the Behavior tab. See [Reviewing agent behavior](./agents#reviewing-agent-behavior).

1. Choose whether to turn on Send a recovery message. It's on by default and sends one message when a signal clears.

1. Select Send test notification to post a sample message to the URL in the field, and confirm that it arrives.

1. Select Save.

## Reviewing delivery history

Use the Recent notifications table to check which messages the backend delivered. It lists the last deliveries with their time, agent, signal, and HTTP status. History is kept for 30 days.

## Understanding signal evaluation

Review how the backend evaluates signals so you know when to expect a message. Every five minutes, the backend evaluates the agents of each instance that has a webhook. It uses the same rollup as the Behavior tab, over the last hour. For each agent and signal:

- When the signal appears, the backend sends one message.
- While the signal persists, the backend sends nothing.
- When the signal clears, the backend sends one recovery message, if Send a recovery message is on.

Switching a signal off closes it silently, without a recovery message. The backend records a failed delivery in the history and doesn't retry it. The next change of state sends again.

## Reading the message format

Read the JSON body of the `POST` to process a message in your own receiver. The `text` field carries a one-line summary in Slack markdown, which Slack renders directly. The remaining fields carry the same information for other receivers:

| Field      | Meaning                                                             |
|------------|---------------------------------------------------------------------|
| `event`    | Always `denial_pattern.changed`.                                    |
| `instance` | `id` and `name` of the instance.                                    |
| `agent`    | `name` and declared `purpose`.                                      |
| `signal`   | `escalation`, `repeated`, `recovered`, or `test`.                   |
| `active`   | `true` when the signal appeared, `false` when it cleared.           |
| `since`    | When the signal was first seen, in [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) format.                 |
| `evidence` | One sentence with the counts behind the signal.                     |
| `counts`   | `allowed`, `denied`, and `escalations` in the window.               |
| `url`      | A link to the agent on the Agents page, built from `publicBaseURL`. |

The message includes no SQL text and no database object names.

### Example: a blocked privilege escalation

Use this example to see the message sent when `aidb` blocks an agent's attempt to switch role:

```json
{
  "text": ":rotating_light: *support-assistant* attempted a privilege escalation on *Production aidb*. aidb blocked it.",
  "event": "denial_pattern.changed",
  "instance": { "id": "3f2c1a9e", "name": "Production aidb" },
  "agent": { "name": "support-assistant", "purpose": "customer_support" },
  "signal": "escalation",
  "active": true,
  "since": "2026-11-23T09:15:00Z",
  "evidence": "1 attempt to switch role was blocked in the last hour.",
  "counts": { "allowed": 42, "denied": 3, "escalations": 1 },
  "url": "https://governance.example.com/agents?agent=support-assistant"
}
```

### Example: a signal clearing

Use this example to see the message sent when a signal clears and Send a recovery message is on. The `signal` is `recovered` and `active` is `false`:

```json
{
  "text": ":white_check_mark: *support-assistant* on *Production aidb* is no longer being repeatedly denied.",
  "event": "denial_pattern.changed",
  "instance": { "id": "3f2c1a9e", "name": "Production aidb" },
  "agent": { "name": "support-assistant", "purpose": "customer_support" },
  "signal": "recovered",
  "active": false,
  "since": "2026-11-23T09:15:00Z",
  "evidence": "2 of 40 governed actions were denied in the last hour.",
  "counts": { "allowed": 38, "denied": 2, "escalations": 0 },
  "url": "https://governance.example.com/agents?agent=support-assistant"
}
```

### Example: routing messages from a custom receiver

Read the structured fields instead of `text` if your receiver isn't Slack. For example, open an incident when `signal` is `escalation` and `active` is `true`. Close it when a `recovered` message arrives for the same `agent.name` and `instance.id`.

## Securing webhook delivery

Review the protections that apply when the backend sends a notification:

- The backend encrypts the webhook URL and doesn't return it to the browser. The dashboard shows only its host name.
- The backend sends the request with the same egress rules as instance connections, controlled by `bff.blockPrivateEgress`. See [Securing your deployment](./administration#securing-your-deployment).
- The backend doesn't follow redirects.
- The backend never logs the URL path, where Slack keeps its token.
- Messages contain no SQL text and no database object names.

## Troubleshooting

Use these checks if notifications don't arrive as expected:

- The Recent notifications table shows an HTTP status other than 2xx — Check the webhook URL and that the receiver accepts a JSON `POST`. If the receiver is on a private address, check `bff.blockPrivateEgress`.
- Send test notification works but no messages arrive — A message is sent only when a signal appears or clears. For Repeated denials, check that the agent has reached the minimum number of governed actions and that the rate has reached the threshold.
- You don't see the bell icon — Check that you're signed in as an administrator, that the instance is a Postgres (aidb_otel) instance, and that `bff.aidbOtelEnabled` and `bff.governanceDecisionsEnabled` are `true`.
