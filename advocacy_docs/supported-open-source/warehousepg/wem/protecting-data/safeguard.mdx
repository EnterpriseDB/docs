Monitor and manage disaster recovery (DR) between the WarehousePG (WHPG) cluster WEM manages and a separate DR standby cluster using the **Safeguard** panel on the left sidebar, built on [WarehousePG Disaster Recovery](/supported-open-source/warehousepg/whpg-dr/) (`whpg-dr`). A DR standby cluster keeps a synced copy of your primary WHPG cluster ready for failover if hardware fails, an outage hits, or an upgrade goes wrong.

## Checking DR readiness

Gauge your recovery health at a glance in the **DR Readiness** section at the top of the page, which shows a single status badge, **Healthy**, **Degraded**, **At risk**, or **Not configured**, driven by the worst of its underlying checks, blocked or suspended archiving, an untrusted PITR state, no base backup, a backup or restore point that's aging, or none at all.

Four tiles give the detail:

- **Recoverable to**: if you failed over right now, how recent the data you'd recover would be, the age of your newest restore point, or your newest backup if you haven't created a restore point yet.
- **Archiving**: whether WAL archiving is currently **Enabled**, **Suspended**, **Disabled**, **Invalid**, or **Inconsistent**, hover it for why.
- **Last base backup**: how long ago your last base backup ran, or **Never** if you haven't taken one.
- **Recovery window**: how far back you could recover to, from your oldest backup up to your newest restore point.

A footer line totals your backup count, backup size, and WAL size. This section reports a stepped recovery point rather than a live, continuously ticking one, `whpg-dr` doesn't expose a WAL-archive-age metric to check against in real time.

## Prerequisites

Before deploying the DR standby, complete the following. Safeguard is optional, and manages DR between your primary cluster and a separate DR standby.

### Installing whpg-dr

Install `edb-whpg-dr` on every host of the primary cluster, following [Installing the package](/supported-open-source/warehousepg/whpg-dr/setting-up-primary/configuring-primary/#installing-the-package).

### Provisioning the DR cluster

If you want the DR standby deployed and kept current in advance, provision the DR cluster now. Otherwise, you don't need it provisioned yet to configure Safeguard and start backups on the primary, `whpg-dr` supports cold DR, provisioning it only once a failure occurs.

See [Installing WarehousePG on the DR cluster](/supported-open-source/warehousepg/whpg-dr/configuring-dr/#installing-warehousepg-on-the-dr-cluster) for the full procedure. Your primary cluster's WEM install doesn't cover the DR coordinator, so also install the [host agent](../installing/host-agent) there.

### Configuring the host agent for Safeguard

Configure the host agent on the primary coordinator, and on the DR coordinator once you provision that cluster. WEM can't derive a DR standby's queue automatically, so set `WEM_TASK_QUEUES` on each. See [Host agent configuration](../reference/host-agent-config#wem-connection) for the full variable reference.

1. Set `WEM_TASK_QUEUES=coordinator-tasks` in `/etc/edb/acp-host-agent/acp-host-agent.conf` on the primary coordinator, and `WEM_TASK_QUEUES=dr-standby-tasks` in the same file on the DR coordinator.
1. Start and enable the host agent on both coordinators:

    ```bash
    sudo systemctl enable --now acp-host-agent
    ```

1. Verify it's connected:

    ```bash
    tail -f /var/log/edb/acp-host-agent/acp-host-agent.log
    ```

!!! Note
    Each section shows an **Agent** indicator (**Live**, **Unreachable**, or **Not configured**), hover it to see the Temporal task queue it's checking. Without a reachable host agent, actions on that cluster stay disabled. Without a DR host agent, run `whpg-dr restore` and `whpg-dr promote` directly on the DR coordinator instead of through WEM.

### Setting up storage

So `whpg-dr` can archive WAL and base backups, set up a storage repository reachable by both clusters. See [Setting up the storage repository](/supported-open-source/warehousepg/whpg-dr/setting-up-primary/storage/) for full details on both backends.

- **POSIX (NFS)**: mount the shared directory read-write at the same path on every coordinator and segment host, in both clusters, owned by `gpadmin`. WEM doesn't mount or create it, and only checks the coordinator, deploying fails with a permission error if the coordinator isn't ready, but a path missing only on segment hosts deploys fine and instead surfaces later as a [WAL archive check failure](/supported-open-source/warehousepg/whpg-dr/troubleshooting/#wal-archive-check-keeps-failing-after-activity) on your first backup.
- **S3-compatible**: have the bucket, region, and read-write credentials ready.

## Setting up disaster recovery

To complete initial setup, work through these sections in order. For the underlying `whpg-dr` command output and progress on whatever's currently running, check **Events** at any point along the way, see [Reviewing configuration history and activity](#reviewing-configuration-history-and-activity).

### Adding a storage repository

Add a storage repository for `whpg-dr` to archive to by selecting **Add Storage Repository** in the **Storage** section, then choosing **POSIX (NFS or Shared filesystem)** or **S3 and Compatible**, and filling in a name and, for S3, a bucket, region (or endpoint URL for an S3-compatible service), and credentials, either static access keys or the host's default AWS credentials. An **Advanced options** section holds a prefix and profile. WEM supports only one storage repository, **Add Storage Repository** is disabled once you've added one. Expand the repository's row for its full path, bucket, and credential details, or use **Edit** and **Delete**, deleting is blocked while the primary or DR cluster still references it.

### Configuring the primary cluster

Configure the primary cluster's backup settings by filling in a cluster name, the storage repository, compression, and a retention policy (a number of backups, days, weeks, or months) in the **Primary Cluster** section, with **Advanced options** for compression level, parallel jobs, WAL prefetch, max archive size, and network compression, see [Configuration files](/supported-open-source/warehousepg/whpg-dr/reference/configuration/) for what each option does. This section shows **Configure Primary Cluster** until you've set one up, this is effectively editing the backup configuration WEM generates, **Edit Primary Cluster** later opens the same fields. Cluster name and storage repository lock once set, since the DR side must match them exactly.

To generate the backup configuration, run `whpg-dr configure backup`, and restart the primary cluster to activate WAL archiving, select **Deploy Configuration**. Deploying is disabled until you've saved a configuration and the primary host agent is reachable. Once deployed, the row's badges summarize its state, **Protected**, **No backups yet**, **Archiving suspended**, **PITR untrusted**, or **Not configured**, alongside a deploy-state badge (**Deployed**, **Changes not deployed**, or **Not deployed**).

Two more actions appear on this row.

- **Check Configuration** validates the deployed `whpg-dr` configuration against the live cluster, effectively `whpg-dr check`. To confirm WAL archiving is actually working before taking your first backup, run it, deploying successfully doesn't guarantee this, see [WAL archive check keeps failing after activity](/supported-open-source/warehousepg/whpg-dr/troubleshooting/#wal-archive-check-keeps-failing-after-activity) if it doesn't pass.
- **Suspend WAL Archiving** (or **Resume**, or **Enable** if archiving isn't on yet) pauses or resumes shipping without a full reconfigure, useful during a storage outage. See [Handling storage outages](/supported-open-source/warehousepg/whpg-dr/setting-up-primary/backups/#handling-storage-outages) for what suspending does to WAL retention and how to recover from it.

### Taking an initial backup

`whpg-dr` needs at least one backup before you can add the DR standby, so select **Take Backup Now** in **Backups & Restore Points**, naming it yourself or leaving it blank for an auto-generated timestamp. This action, and creating a restore point, are disabled while the primary isn't configured, a job is already running, the topology has drifted, or archiving is suspended, invalid, or inconsistent.

See [Managing backups and restore points](#managing-backups-and-restore-points) for the rest of this section once setup is done.

### Adding the DR cluster

Add the DR cluster's configuration by selecting **Add DR Cluster** in the **DR Cluster** section, which stays empty until the primary has at least one backup, and entering a name, the storage repository, a coordinator host, coordinator data directory, segment hosts, data directory, and directory prefix, pre-filled from the primary's discovered topology where possible. Cluster name and compression are inherited from the primary and shown read-only. **Edit DR Cluster** later opens the same fields. WEM supports only one DR cluster.

Select **Deploy Configuration** to generate the restore configuration, run `whpg-dr configure restore`, and restart the DR cluster, this step doesn't restore any data, the DR cluster stays empty until you run a restore. Once both clusters are deployed, see [Checking DR readiness](#checking-dr-readiness) and [Restoring and promoting the DR cluster](#restoring-and-promoting-the-dr-cluster).

## Managing backups and restore points

Once setup is done, handle ongoing backup activity through **Backups & Restore Points**. Every action on this tab requires the primary cluster configured.

- **Take Backup Now** and **Create Restore Point** work as during setup, each with an optional name.
- The table lists every base backup, newest first, with status, mode (**Full** or **Rsync**), age, size, WAL size, and restore point count. Restore points nest under the base backup they belong to, expand a backup's row to see them alongside its per-segment detail. A restore point only appears as its own top-level row if its base backup was later deleted (an orphan).
- **Verify** runs `whpg-dr check-backup` to confirm a backup's files are present and accessible on every segment.
- **Delete** removes a backup and every restore point that belongs to it, retain at least one backup at all times.
- A retention summary shows how many backups are currently eligible for pruning under your configured policy.

## Restoring and promoting the DR cluster

When you need to fail over, or to test your recovery plan, restore and promote the standby using the **DR Cluster** section. Complete these two actions in order.

!!! Warning
    A restore wipes the DR cluster's current data directories and replaces them with the restored backup. Confirm you're targeting the correct cluster before proceeding.

Choose a restore target, the latest restore point or a specific one, and a restore type, **Full** or **Delta** (delta replays WAL on top of an already-restored cluster instead of starting empty, and is disabled when there's no prior restore to build on, the cluster is already promoted, or a restore is already running), by selecting **Run Restore**. **Advanced options** hold a WAL replay timeout and an option to supersede an unresolved restore goal without confirming. To run it as a dry run and see the underlying `whpg-dr` command before you confirm for real, select **Preview This Restore** first. If a restore is interrupted, **Resume Failed Restore** continues it without asking for the original parameters again.

The row's badge tracks restore progress, **Not restored**, **Restore in progress**, **Restore unresolved**, **Replay complete | promote blocked**, **Ready to promote**, or **Promoted**, and its expanded view includes a per-segment status table with each segment's replay progress.

!!! Warning
    A promote turns the DR standby into a live, writable primary and ends its role as a DR target. Confirm you're targeting the correct cluster before proceeding.

Once a restore shows **Ready to promote**, select **Promote Cluster** and type to confirm. Promoting rewrites the segment configuration and removes mirror entries, but doesn't start the cluster for you, run `gpstart` afterward. If WEM finds an unresolved restore state or a segment that isn't ready, it lists the issues and lets you **Override Checks And Promote** instead, understand the risk before using it.

Safeguard treats promote as a failover action, treat the DR cluster as your new production cluster afterward, and configure DR again in the other direction if you need to fail back later.

## Reviewing configuration history and activity

Review two tables at the bottom of the page, both filterable and paginated.

- **Configuration History** lists every saved, deployed, or synced configuration change, for both the primary and DR cluster, when it happened, who made it, its source (**Save**, **Deploy**, **Host Sync**, **Import**, or **Rollback**, qualified with which cluster it applied to), and what changed. A **Host Sync** row means Safeguard picked up a manual edit to the `whpg-dr` configuration file itself, there's no separate drift banner, it's recorded here instead. Roll back to an earlier entry from its row, and check **Also deploy to host** to redeploy it immediately rather than just restoring the saved values.
- **Events** lists every background job Safeguard has run, deploys, backups, restore points, restores, promotions, and WAL archiving suspend/resume, with its status (**Success**, **Info**, **Running**, **Warning**, or **Error**) and full detail on expansion. Error rows auto-expand until you dismiss them.
