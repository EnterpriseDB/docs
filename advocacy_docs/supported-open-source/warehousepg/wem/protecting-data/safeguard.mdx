Use the **Safeguard** panel on the left sidebar to monitor and manage [WarehousePG Disaster Recovery](/supported-open-source/warehousepg/whpg-dr/). 

!!! Note
Safeguard requires the host agent and `whpg-dr` to be installed on both the primary and DR coordinators, plus a storage repository, reachable by both clusters, for `whpg-dr` to archive WAL and base backups to. See [Configuring Safeguard](../installing/safeguard) if you haven't set this up yet.
!!!

## Monitoring DR status

Use the **Status** tab to check whether your primary and DR clusters are healthy and ready for a failover.

- Check **WAL Continuity** to confirm WAL archiving is flowing without gaps. Investigate immediately if it shows **Failed**, archiving has stopped and your DR standby is falling behind.
- Check **Last Restore Point** to see how current your DR standby is.
- Check **Backup Count** to confirm you're retaining enough backups for your recovery requirements.
- Find a specific point to restore to using the **Restore Point Timeline**, filtered by date range.
- Before failing over, confirm the DR cluster's readiness in the DR section, which shows the coordinator's host, connection status, and whether it's ready to promote, in recovery, or already promoted to primary.

## Configuring Safeguard

Use the **Configuration** tab to set up or modify your DR configuration by generating a `whpg-dr` configuration from the fields below and deploy it through the host agent.

### Setting global options

Select **Edit Configuration** on the Configuration tab before setting these fields.

- **Cluster Name**: choose a name for this `whpg-dr` cluster. WEM embeds this value directly into the configuration it generates and uses it afterwards for status checks, so avoid changing it later. The field defaults to a placeholder value, so set it explicitly.
- **Checkpoint Interval (min)**: how often WEM checks WAL continuity.
- **Storage**: choose **Filesystem / NFS** and a path, or **S3** and a bucket, region, and credentials, plus an optional prefix and custom endpoint URL. WEM doesn't mount the NFS share for you. Mount it read-write at that path on every coordinator and segment host, in both clusters, before deploying. See [Setting up the storage repository](/supported-open-source/warehousepg/whpg-dr/setting-up-primary/storage/).
- **Barman & Retention**: set compression, compression level, network compression, WAL prefetch count, and a retention policy, keeping all backups, a fixed count, or a number of days. See [Configuration files](/supported-open-source/warehousepg/whpg-dr/reference/configuration/) for full reference.

Select **Save** at the top right of the tab once you finish.

### Configuring the primary cluster

Select **Edit Configuration** on the Configuration tab before starting these steps.

1. Select **Discover Primary Cluster** to populate the coordinator host, coordinator data directory, and segment hosts automatically, queried live from the primary WarehousePG cluster itself rather than from any existing `whpg-dr` configuration.
1. Select **Save**. **Deploy Primary** only appears once a saved configuration exists, so it stays hidden until you save.
1. Select **Deploy Primary** to generate the backup configuration and push it to the primary coordinator through its host agent, which runs `whpg-dr configure backup` there.
1. Check the **Tasks** tab to confirm the deploy job completed successfully.

!!! Note
You must take at least one base backup on the primary cluster from the **Backups** tab before configuring the DR standby. See [Managing backups](#managing-backups).
!!!

### Configuring the DR standby

Select **Edit Configuration** on the Configuration tab before starting these steps.

1. Enter the **DR Coordinator Host**.
1. With **Mirror Primary Topology** set to **Yes**, select **Copy from Primary** to pre-fill the DR fields from the primary's topology, then replace **Segment Hosts** with the DR cluster's real hostnames and adjust the **DR Data Directory** and **DR Data Directory Prefix** to match. Set **Mirror Primary Topology** to **No** to enter the DR cluster's topology manually instead.
1. Select **Save**. **Deploy DR** only appears once a saved configuration includes a DR Coordinator Host, so it stays hidden until you save again after filling in this section.
1. Select **Deploy DR** to generate the restore configuration and push it to the DR coordinator through its host agent, which runs `whpg-dr configure restore` there. This requires the DR coordinator's data directory to already be set, either through **Copy from Primary** or entered manually.
1. Check the **Tasks** tab to confirm the deploy job completed successfully.

!!! Note
    The form has no field for a non-default Postgres port. `whpg-dr` reads the port from the `PGPORT` environment variable in the host agent's own environment, falling back to `5432` if it's unset. If your cluster runs on a non-default port, set `PGPORT`.

## Managing backups

Review base backup and WAL archiving activity for the primary cluster from the **Backups** tab, including the timestamp of the last base backup and hourly WAL growth.

- Select **Create Backup** to run a new base backup on the primary cluster, optionally naming it. Deploying Safeguard on the primary doesn't take a backup by itself, you need at least one base backup here before you can deploy the DR standby, or `whpg-dr` has nothing to restore from.
- Select **Create Restore Point** to mark the current point in time as a named, recoverable point once a base backup exists.
- Both actions require Safeguard to already be configured (deployed) on the primary cluster.
- Check the **Tasks** tab to confirm the backup or restore point job completed successfully.

## Restoring and promoting the DR cluster

Use the **Restore** tab to manage the DR standby, from applying a restore to promoting it into a live primary. Restore and promote operations run directly from this tab when the DR cluster is reachable through the host agent.

### Restoring the DR cluster

!!! Warning
    A restore wipes the DR cluster's current data directories and replaces them with the restored backup. Confirm you're targeting the correct cluster before proceeding.

Pick a restore point from the **Restore Point Timeline** on the **Status** tab and restore to it. The restore applies the base backup associated with that point to every segment data directory, then replays WAL forward to it. Once replay finishes, the segments stop in recovery mode and the cluster stays offline, rejecting client connections until you promote it. See [Performing the restore](/supported-open-source/warehousepg/whpg-dr/performing-disaster-recovery/cold-dr#performing-the-restore) for details. 

Restores are forward-only. Advancing to a later restore point replays only the WAL difference on top of the existing data directories. Going back to an earlier point needs a fresh restore instead. See [Advancing to a later restore point](/supported-open-source/warehousepg/whpg-dr/performing-disaster-recovery/cold-dr#advancing-to-a-later-restore-point) and [Performing a fresh restore](/supported-open-source/warehousepg/whpg-dr/performing-disaster-recovery/cold-dr#performing-a-fresh-restore).

Check the **Tasks** tab to confirm the restore job completed successfully.

### Promoting the DR cluster

!!! Warning
    A promote turns the DR standby into a live, writable primary and ends its role as a DR target. Confirm you're targeting the correct cluster before proceeding.

Promote the DR cluster once its restore is complete to bring it online as a writable primary that accepts client connections. Promotion is blocked while the cluster has an unfinished or failed restore. 

Safeguard treats promote as a failover action. Once you promote through this tab, treat the DR cluster as your new production cluster, and expect to configure DR again in the other direction if you need to fail back. This behavior differs from `whpg-dr`, which also supports promoting the DR cluster on its own for point-in-time recovery, inspecting or extracting data while the primary keeps running, then shutting the DR cluster back down without a failover. See [Recovering individual objects](/supported-open-source/warehousepg/whpg-dr/performing-disaster-recovery/pitr#recovering-individual-objects) for that CLI workflow. 

Promoting a cluster doesn't restore mirrors or a standby coordinator, so the promoted cluster starts with only primary segments. See [Adding mirrors and standby coordinator](/supported-open-source/warehousepg/whpg-dr/performing-disaster-recovery/cold-dr#adding-mirrors-and-standby-coordinator) to add them separately afterward.
