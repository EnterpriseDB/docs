# EDB Postgres Distributed 5.10.0 release notes

Released: 19 November 2026

EDB Postgres Distributed 5.10.0 includes an enhancement and bug fixes focused on improving stability and reliability. For a list of known issues, see [Known issues and limitations](https://www.enterprisedb.com/docs/pgd/5.10/known_issues/).

## Highlights

- [Raft PreVote](https://www.enterprisedb.com/docs/pgd/5.10/routing/raft/04_raft_elections_in_depth/#raft-leader-elections-and-prevote): PreVote, introduced in PGD 6, is now backported to PGD 5. A node isolated by an unstable network link no longer forces a Raft leader election when it reconnects, so a healthy leader isn't displaced and clusters recover from network flapping without disruption. No configuration is required. PreVote takes effect once all nodes run PGD 5.10 and applies to the top-level group.

## Bug Fixes

<table class="table w-100"><thead><tr><th>Component</th><th>Version</th><th>Description</th><th width="10%">Addresses</th></tr></thead><tbody>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed a hard hang between a writer and the receiver in CAMO.</summary><p>A receiver restart, for example after the origin node was partitioned and then recovered, could hang when the downstream node had CAMO transactions in its commit decisions. The receiver waited on a flush while the writers waited for the full commit decision feedback queues that the receiver never emptied. The deadlock detector didn't detect this hang, and only a server restart resolved it. This issue has been present since 5.9.1.</p>
</details></td><td>65610</td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed a misdirected signal from the writer that could restart an instance in a container.</summary><p>After a flush, the writer woke the receiver with a <code>kill()</code> call whose two arguments were swapped. On a normal host the call failed, since receiver PIDs are larger than the highest signal number, and the receiver waited up to 1 s for the flush confirmation unless something else woke it. In a container or another fresh PID namespace, the call could hit a Postgres process: with a receiver at PID 24, the writer sent signal 24 (<code>SIGXCPU</code>) to the checkpointer at PID 10, and the postmaster restarted the instance. The writer now wakes the receiver with the arguments in order, and only after it has confirmed the flush.</p>
</details></td><td>66414</td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed the Raft term of exported consensus snapshots.</summary><p><code>bdr.consensus_snapshot_export()</code> labeled a snapshot with the node's current Raft term instead of the term of the last entry the snapshot includes. After an election the two differ. Nodes that imported such a snapshot then disagreed with the exporting node about that entry, and when the exporting node was elected leader again, the Raft group committed no entries until the next snapshot sync. Snapshots now carry the term of their last entry.</p>
</details></td><td></td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed the loss of a committed Raft entry when the first node joins a Raft group.</summary><p>A Raft leader treated a node added while it was leader as silent until the node's first response. When the first node to join a Raft group became a voter before the leader's first heartbeat, the leader stepped down without having sent a heartbeat. The joining nodes then elected a leader with an empty log while the old leader held a committed entry, and that entry was truncated. The leader now counts a node it adds as heard from, as it does for the nodes present at its election.</p>
</details></td><td></td></tr>
<tr><td>PGD CLI</td><td>5.10.0</td><td><details><summary>Fixed <code>pgd node upgrade</code> restoring replication origins at the wrong position.</summary><p><code>pgd node upgrade</code> restores each replication origin at the highest progress of its writer origins, but its patterns for the writer origins didn't match their names:</p> <ul> <li>An origin whose ID contains a hex letter lost its writer origins and was restored behind them.</li> <li>An origin could take the progress of another origin's writers (origin <code>0x2</code> matched the writers of <code>0x21</code>). Its subscription then started ahead in the wrong peer's WAL and skipped transactions.</li> <li>A writer origin without recorded progress was taken as the furthest ahead.</li> <li>The origins of a database whose name starts with <code>writer</code> weren't restored at all.</li> </ul> <p>The writer origins are now matched by their exact names.</p>
</details></td><td></td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed missing replication slots for witness nodes after concurrent joins.</summary><p>Witnesses skipped join serialization, though they need slots in both directions. A witness joining concurrently with other nodes could end up without some slots, breaking later operations such as node parting. Witnesses are now serialized like data nodes.</p>
</details></td><td></td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed a hang when a writer restarts while a global lock is held.</summary><p>If a writer or a node restarted after a global lock was acquired (after <code>ACQUIRE</code> or <code>ACQUIRE FINISH</code>, or after DDL had committed or prepared but before the lock was released), the manager or the writer doing DDL could hang forever. Locks recovered after a restart are now rebuilt without re-acquiring them, writers for the lock's origin are let through, and <code>FINISH</code> and <code>RELEASE</code> are routed to the same writer.</p>
</details></td><td></td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed <code>update_recently_deleted</code> conflicts detected as <code>update_missing</code>.</summary><p>An update to a recently deleted row could be classified as <code>update_missing</code>, so the default <code>insert_or_skip</code> resolver inserted the deleted row again. The conflict is now detected correctly.</p>
</details></td><td></td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed a memory leak in CAMO transactions.</summary><p>Fixed a memory leak where every commit under a CAMO commit scope leaked a small buffer in the backend's top memory context. On long-lived connections, such as pooled connections to the write leader, the leak caused unbounded memory growth and could lead to out-of-memory conditions. The same leak on the commit error path for other commit scopes that use group commit is also fixed.</p>
</details></td><td>65147</td></tr>
<tr><td>BDR</td><td>5.10.0</td><td><details><summary>Fixed conflict detection for EXCLUDE constraints over an index expression.</summary><p>Conflicts on an EXCLUDE constraint that indexes an expression, for example a <code>tstzrange(time_from, time_to)</code> column, weren't detected. The writer failed with a plain <code>23P01</code> error and retried until it exited, no conflict was logged to <code>bdr.conflict_history</code>, the configured conflict resolver wasn't used, and replication from that peer was blocked. Conflict detection now supports EXCLUDE constraints over an index expression, and these conflicts are resolved like other EXCLUDE conflicts.</p>

That unwound out of the finish function and skipped writer cleanup, closing the connection, and the remaining exit callbacks. During process exit, these failures are now logged as warnings and the cleanup runs to completion.</p>
</details></td><td></td></tr>

Replacing one name by the other in the configuration file failed on every reload until a restart: the postmaster shut down, and in other processes the statement that processed the reload failed. Meanwhile the node ran with the default timeout. With both names in the configuration file, the server didn't start. Now:</p> <ul> <li>A conflicting line in the configuration file is logged and skipped, at startup and on reload. On a reload the name already in effect wins; at startup, <code>bdr.raft_global_election_timeout</code>.</li> <li>One reload applies an edit of the file that replaces one name by the other.</li> <li><code>ALTER SYSTEM</code> still refuses to set the second name. <code>RESET</code> the first one and reload before you set it.</li> <li>Raft applies a new timeout at the next consensus restart, as before.</li> </ul>

PGD now publishes the change before it notifies any worker.</p>

As a result, <code>bdr.get_raft_status()</code> reported a <code>leader_id</code> of 0 on the leader, and the PGD CLI clock-drift check failed.
